## S0 — actual packages and deployment cost

The published [Conductor server v3.32.4 POM](https://repo.maven.apache.org/maven2/org/conductoross/conductor-server/3.32.4/conductor-server-3.32.4.pom) declares `io.orkes.queues:orkes-conductor-queues:2.0.0.rc3` at runtime. A ZIP-directory inspection located that JAR inside the published boot artifact. The [queue POM](https://repo.maven.apache.org/maven2/io/orkes/queues/orkes-conductor-queues/2.0.0.rc3/orkes-conductor-queues-2.0.0.rc3.pom) names the [Orkes Community License](https://github.com/orkes-io/licenses/blob/14cd5d6b0619399c205a022cc7b512734ea51911/community/LICENSE.txt); Article 3.3 restricts third-party service and competitive-product uses. The Apache 2.0 [core source license](https://github.com/conductor-oss/conductor/blob/v3.32.4/LICENSE) does not establish rights for that assembled package. This is an unresolved product-rights finding, **not** a legal ruling or a Conductor runtime defect. The suspected PostgreSQL-only alternative was source-inspected but not built, dependency-audited or booted. Conductor S1–S4 were therefore not run.

The [Kestra v2.0.3](https://github.com/kestra-io/kestra/releases/tag/v2.0.3) executable matched its release SHA-256 `b4b4518a617f93965dcf98c9673beda3dad2b6d9d1780ad8b9a945e437975ab4`. Its main class required **JDK 25**; JDK 21 failed, despite an older standalone guide saying 21+. On macOS arm64 the initial local launcher managed Kestra and an isolated PostgreSQL 16.15 cluster, using PostgreSQL for the repository and queue. It published a `Log` workflow and recovered a `Log → Pause → Log` execution after both processes stopped. That first trial used a Homebrew PostgreSQL binary; the separate copied-bundle follow-on is described below. The JAR was 124.3 MiB, the unpacked JDK 294 MiB, and the small database 65 MiB; warm idle Kestra was about 650 MiB RSS with a 1 GiB heap cap. These are observations, not a product footprint or capacity target. Kestra [recommends at least 4 GiB RAM and 2 vCPU](https://kestra.io/docs/administrator-guide/requirements) for standalone.

The S0 follow-on copied the Kestra JAR, Temurin JDK 25, PostgreSQL keg and needed dynamic libraries into an isolated **macOS arm64 host-local bundle**. After patching Mach-O load paths and ad hoc signing, a single launcher initialized bundled PostgreSQL with SCRAM authentication and started Kestra from a scrubbed `env -i` process environment. A `Log → Pause → Log` execution remained `PAUSED` after both processes stopped and the same launcher restarted; it then resumed to `SUCCESS`. A static scan found no Homebrew load paths in 143 bundled Mach-O files, and the live PostgreSQL process had no `/opt/homebrew` file references. The trial bundle was about **609 MiB including 66 MiB of state**. This proves one-command **local startup on this host**, not clean-machine portability, an installer, notarization, upgrade/backup behavior, all-platform support or final distribution rights.

Kestra's pinned [core license](https://github.com/kestra-io/kestra/blob/v2.0.3/LICENSE) is Apache 2.0. A bounded audit found published license declarations for 158 of 159 embedded Maven coordinates, without an explicit Conductor-like product-use restriction in those declarations. One shaded `isorelax` component has unclear license/notice provenance ([published POM](https://repo.maven.apache.org/maven2/com/sun/xml/bind/jaxb/isorelax/20090621/isorelax-20090621.pom); [Woodstox notice issue](https://github.com/FasterXML/woodstox/issues/130)). The final bundle also needs ordinary notices and JDK/PostgreSQL review. **Redistribution is not yet cleared.** Kestra OSS required Basic Auth in the test; [its documentation says disabling it is ignored](https://kestra.io/docs/administrator-guide/basic-auth-troubleshooting). The product still needs an independently enforced publisher/invocation boundary.

## S1–S4 — what the system actually did

S1 used Kestra's live v2 API, PostgreSQL persistence and one standalone server. After restarting Kestra and PostgreSQL, the same execution remained `PAUSED`. Of eight concurrent resume requests, one returned HTTP 200 and seven returned HTTP 409; one downstream task ran. Across five resume/kill races, one execution succeeded and four were killed, each with at most one downstream run. Some races returned HTTP 200 to both control callers, so the durable terminal execution state, not the response alone, is authoritative. These flows had no external side effects. The actual resume route was `/api/v1/main/executions/{id}/actions/resume` with multipart input, consistent with the live [Kestra OpenAPI](https://kestra.io/kestra.yml).

S2 ran an actual Strands 1.57.0 tool loop with a deterministic model fixture. The same harness code served an ordinary capability and a factory Director with distinct identities, state directories, workspaces and A2A endpoints. Its official A2A SDK 0.3.26 transport advertised protocol 0.3.0. The initial six process tests killed and restarted a waiting factory, rejected an old Director incarnation, suppressed concurrent duplicate logical assignments, retrieved a nested factory result and propagated a parent cancellation. Those parent/child cases used a fixed one-checkpoint engine fixture, so **native child composition is not proved**. A reusable A2A projection Adapter kept completion tied to accepted durable state rather than conversation completion.

The S2 follow-on then integrated **one real Kestra native flow** behind the same harness Interface. The live A2A Director request created a pinned-revision execution, which reached a native Pause. Eight concurrent repeat starts retained one logical/native execution. Two SIGKILL/restarts preserved identity, pending work and later accepted artifact state; an old Director incarnation and unauthorized or no-review decisions were rejected. Eight repeated decisions produced one observed resume request and one successful downstream task run. Kestra ended `SUCCESS`, and A2A completion carried the accepted artifact. The combined suite was **7 passed in 18.39 seconds**. Native `tasks/get` reconciliation did not need a model turn. This proves a useful harness/engine seam for one Pause, while create-response ambiguity currently fails closed and resume crash windows, multiple Pause iterations, native child/cancel behavior and throughput remain open. The spike code holds a SQLite ownership transaction across some network calls; that is not an endorsed production design. Test credentials, model decisions and evaluator decisions remain fixtures. [Pinned Kestra execution controller](https://github.com/kestra-io/kestra/blob/v2.0.3/webserver/src/main/java/io/kestra/webserver/controllers/api/ExecutionController.java) · [Pinned task-output controller](https://github.com/kestra-io/kestra/blob/v2.0.3/webserver/src/main/java/io/kestra/webserver/controllers/api/OutputController.java).

S3 published native Kestra YAML and ran two parallel synthetic research branches, synthesis, one repair/re-review, a Director pause and a **synthetic delivery placeholder** after resume. No independently authorized review or real delivery effect ran. Changing a child flow to v2 while old parents waited preserved the explicitly pinned child v1; an old **unpinned** parent later used v2. Publication created a new revision rather than overwriting revision 1 in the tested API path. The product publisher must therefore pin the transitive flow dependencies it relies on. Kestra validated and published a schema-valid delivery-only graph; it was not executed. Engine validation does not enforce Exomachina's Quality gate or destination policy.

S4 used three complementary cases. A custom HTTP receiver with idempotency/discovery survived a lost acceptance reply with one effect; a receiver without either guarantee remained explicitly `unknown`, without unsafe redispatch. A real Kestra `Log → Pause → Log` flow then survived product exit before and after resume acknowledgement with one downstream run, though that remote receiver was custom HTTP. Finally, one native Kestra flow invoked the live Strands A2A capability, retained its completed structured artifact, paused, and resumed only after a product ledger accepted the exact artifact digest from an independent Quality fixture. Forced product exits before reading output, before resume and after resume were reconciled; one assignment, gate and delivery task ran. This combined case proves a useful engine/product seam, but it does not inject a lost response between Kestra's HTTP task and A2A, nor does it cover asynchronous input-required/auth-required tasks or a real reviewer.

## Architectural consequence and next decision

Keep the agreed responsibility split. The native engine owns graph dispatch, waits, retries and its execution history. The harness's Factory Module owns permitted publication, stable instance identity, current Director authority, exact-artifact acceptance and a small intent/outbox ledger for cross-system commands. Remote services own their task outcome and must advertise discovery or idempotency where automatic redispatch could duplicate effects. Do not infer acceptance from HTTP 200, a model sentence or the end of a Strands conversation. The S3 bypass flow shows why publication policy must be enforced before native registration; the S4 crashes show why the product decision and engine continuation cannot be treated as one transaction.

**Proceed with Kestra OSS v2.0.3 as the provisional development baseline behind the customized Strands Factory Module.** It has the strongest observed fit under the newly required local operating model. This is a reversible implementation choice, not a commitment to distribute or operate it in production. The later Conductor source variant re-enters as a technical candidate, but needs a reproducible product package and comparable S1–S4 tests. Before a product-engine commitment, close Kestra's **clean-machine one-install package** and final distribution review, prove the supported recovery path for ambiguous native creation/resume and direct engine-API bypass, and assess whether its resource, port and upgrade cost fits the intended installation. The host-local bundled launcher and narrow harness-to-native-Pause seam passed; full lifecycle ownership has not. Two harness instances sharing a locally managed helper lifecycle and collision-free ports/state also remain to be qualified. If those gates fail, reopen the lighter-runtime screen or a narrowly scoped alternative. Full S5 Engineering and optional autoresearch tests, load, backup, upgrade, multi-customer isolation, and A2A 1.x belong to later qualification; sandbox work remains deferred until a concrete blocker.
