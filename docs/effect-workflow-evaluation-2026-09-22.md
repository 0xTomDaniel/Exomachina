> **Later decision, 23 September:** Effect is the [conditional development runner-up](engine-reassessment-2026-09-23.md), behind Temporal's stable interpreter. The original trial below remains historical; later frozen composition, held-call and upgrade reports are linked from the reassessment.

22 September 2026 · Source review and bounded local trial · **Focused contender, unscored; no product engine selected**

The [pinned v3 countertrial](../tools/spikes/2026-09-22/countertrials/effect_workflow/result.md) ran a real SQL-backed `SingleRunner` with SQLite in one Node process. An approval wait survived SIGKILL and a fresh process delivered its completion. Warm idle was about **185 MiB RSS for that helper alone**; the minimal package tree was about 83 MiB on the trial host. This is narrower than a whole-install or production footprint result. Two concurrent approval callers both observed successful completion while the fixture's delivery Activity logged once; this is one bounded duplicate-signal observation, not an exactly-once external-effect guarantee.

## Why it belongs in the comparison

The earlier comparison grouped Effect with code-defined workflow systems and did not separately evaluate `@effect/workflow` with `@effect/cluster`. That missed a relevant deployment option. [Effect workflows](https://github.com/Effect-TS/effect/blob/v3/packages/workflow/README.md) provide typed definitions, durable activities, retries/compensation, timers, external waits and child workflow composition. The [SQL-backed single-node runner](https://github.com/Effect-TS/effect/blob/v3/packages/cluster/src/SingleRunner.ts) can run as a bundled local helper. The inspected packages are [MIT licensed](https://github.com/Effect-TS/effect/blob/main/LICENSE); no Docker, JVM or separately installed server is inherent in this topology. These are source-level properties, not a proven Exomachina distribution or measured full installation.

The candidate topology is **one automatically managed local Node helper and SQLite store per installation**, serving multiple Python Strands harness instances. Each harness retains its own identity and durable state; its agent remains the factory Director. The helper's [generated HTTP workflow surface](https://github.com/Effect-TS/effect/blob/v3/packages/workflow/src/WorkflowProxy.ts) is a possible transport seam, not an A2A service or authorization boundary by itself. Exomachina would own helper lifecycle, harness-to-run authorization, A2A task reconciliation, artifact acceptance and permitted external effects. Start with one owner of the SQLite file; multi-runner failover is a separate topology requiring proof.

## The differentiating authoring cost

Effect's documented workflows are **TypeScript programs** registered with the workflow engine. It does not provide a managed JSON/YAML factory-definition catalog, semantic validator and publication/version service equivalent to the native-definition candidates. Generating and deploying new TypeScript for every agent-authored factory would reintroduce code rollout and code-execution policy. A preinstalled interpreter for approved, immutable factory documents could permit publication without restarting the helper, but Exomachina would then own the document language, validation, version closure, run binding, migration policy and publication API. Unique runtime registration of generated workflow tags is another plausible mechanism; its restart and version semantics have not been tested. Neither mechanism receives native-DSL credit until demonstrated.

Effect does supply scheduling and durable workflow primitives, so this is not equivalent to building a workflow engine from snapshots. The product-specific catalog and acceptance rules are common work across candidates; the **extra differentiating cost** is an agent-friendly, governed definition layer. Whether that is smaller than bundling and operating a declarative engine remains open.

### A bounded declarative layer is feasible, but its semantics are the work

The simplest candidate is **one preinstalled `FactoryRun` workflow** that interprets approved factory documents. Its Interface accepts a published definition digest, run identity and input; the run binds that immutable definition and its child/capability/policy closure before executing. A Factory Definition Module validates and publishes documents, then the interpreter maps a finite node vocabulary—assignment, typed conditional routing, parallel/join, bounded loop (including review/repair), nested factory and Director wait—onto Effect Activities, durable waits and child workflows. **The node vocabulary is closed initially; graph composition is flexible.** Agents can publish new arrangements without a template or helper rollout. Required Quality acceptance and controlled delivery are enforced by policy, not author-omittable optional nodes. A new primitive or incompatible interpreter behavior still requires a tested code release. This is an Effect-specific Implementation, not a portable abstraction across all engines.

Avoid generating and registering a new `Workflow.make` tag for each authored factory as the initial path. Registration is code-driven, and repeat names are cached/ignored; restart would need to register every active version before messages resume. The stable interpreter keeps the runtime registration fixed. Within it, every logical Activity **and durable wait** occurrence needs a deterministic unique name derived from node identity and bounded loop/fan-out position, because the [cluster engine keys their records by name within an execution](https://github.com/Effect-TS/effect/blob/v3/packages/cluster/src/ClusterWorkflowEngine.ts). A retry that presents the same run ID with a different definition digest must be rejected before execution; an idempotency key alone does not validate version binding. Remote A2A effects remain behind Activities and the common reconciliation Adapter, not plain workflow code.

The syntax itself is small: [Temporal's official example](https://github.com/temporalio/samples-typescript/blob/main/dsl-interpreter/src/workflows.ts) interprets sequence, parallel and activity calls in about 40 lines. That example does not provide our publication, review or recovery rules. The **incremental Effect work** is chiefly the restricted grammar and typed dataflow, durable interpreter, definition storage/version compatibility, factory-level diagnostics and replay/fault tests. Semantic checks that prevent review bypass and unbounded work, immutable child bindings, the A2A lifecycle, artifact acceptance, budgets and actor authorization are **common product work** whichever engine we choose. A purpose-built finite grammar may make the semantic checks easier than constraining a broad native DSL; native engines do supply structural validation, managed definitions and execution inspection that Effect would not give us for free.

As a planning hypothesis for one experienced engineer *after common contracts and the A2A Adapter exist*: a sequence/approval demonstration is a few days to two weeks; a useful first restricted layer including the reference factory and publisher is roughly **4–8 engineer-weeks**; robust migration, diagnostics and adversarial multi-instance recovery could add **8–16 engineer-weeks**. These are deliberately low-confidence scope estimates, not measurements or a promise of elapsed calendar time. They assume flexible composition of the approved nodes with typed routing and bounded loops, **not** arbitrary edge semantics, executable expressions or runtime graph rewiring; those would increase scope substantially. A native-definition engine still needs policy checks and publication governance, so its advantage is smaller than the entire layer estimate. Effect's authoring gap is material, but not a categorical dealbreaker if we keep the vocabulary finite.

The next proof should publish v1, suspend a run, publish v2 while the helper stays up, start v2, kill/restart the helper and show the waiting run still executes v1. Add two competing signals and one crash around remote dispatch, count non-fixture product code, and measure the whole Strands-plus-helper package. That would test both the claimed no-rollout authoring advantage and the actual incremental implementation cost.

## Version and operating cautions

The bounded trial pins the v3 `@effect/cluster` and `@effect/workflow` packages. The current [v4 migration guide](https://github.com/Effect-TS/effect/blob/main/MIGRATION.md) folds cluster and workflow APIs into `effect` and marks them unstable during the release-candidate period. Pin one line and budget an API migration rather than treating v3/v4 examples as interchangeable. The v3 Node SQLite adapter uses a native driver; the [v4 SQLite contention fix](https://github.com/Effect-TS/effect/pull/7162) should not be credited to that v3 adapter without a backport or reproduction. A previously reported [SQL lease-refresh fault](https://github.com/Effect-TS/effect/issues/6508) is closed and [fixed](https://github.com/Effect-TS/effect/pull/6516) in the inspected current v3 cluster package and v4; retain its failure mode as a later multi-runner regression test, not a current exclusion.

The [Effect Days 2025 Cluster talk](https://www.youtube.com/watch?v=4lEDdMuTDJg) explains the actor-like single-writer entity model ([03:31](https://www.youtube.com/watch?v=4lEDdMuTDJg&t=211s)), persistent versus volatile messages ([07:41](https://www.youtube.com/watch?v=4lEDdMuTDJg&t=461s)), and SQL-backed runner composition ([14:27](https://www.youtube.com/watch?v=4lEDdMuTDJg&t=867s)). It is **historical architecture evidence**, not a current workflow demonstration: [at 22:24](https://www.youtube.com/watch?v=4lEDdMuTDJg&t=1344s) workflows were described as future work, and [at 24:02](https://www.youtube.com/watch?v=4lEDdMuTDJg&t=1442s) Cluster was called alpha at that time. The on-stage persistence/deduplication demonstration [did not complete as intended](https://www.youtube.com/watch?v=4lEDdMuTDJg&t=1108s); that is not a reproduced defect in the pinned 2026 trial. Current [workflow source](https://github.com/Effect-TS/effect/blob/v3/packages/workflow/README.md) and the local SQL-backed recovery trial are the relevant present evidence. The talk shows no managed declarative factory language.

## Decision gates

1. Extend the observed SQL-backed local pause/restart result to the **whole package** with one and two Strands harnesses. Measure comparable idle, paused and active memory, initialized disk and process count before calling it light.
2. Publish a valid v2 factory while a v1 run waits, then prove v1 resumes with its original definition and v2 starts without helper rollout. Count every line of interpreter/publisher and transitive dependency pinning as product ownership.
3. Test duplicate and reordered signals, concurrent same-run delivery, lost remote submission acknowledgement, and worker/helper failure without duplicate accepted artifacts or unsafe external effects. A remote A2A peer's own idempotency must be identified separately.
4. Prove two harness identities can use one helper without crossing run, credential, artifact or Director authority boundaries. Verify one harness exiting does not stop the other's work.
5. Package cleanly with one install/start command, no Docker prerequisite, reproducible native dependencies and upgrade/backup ownership. Confirm redistribution rights of the assembled artifact, not only the repository license.

The bounded local trial is an early screen, not E01–E10 or production qualification. Keep Effect unscored until it receives the same 65-feature evidence review and a comparable selection-ownership assessment. Its credible position is a **compact single-helper topology with substantial authoring-layer work**, not an exclusion or a selected replacement for Kestra.
