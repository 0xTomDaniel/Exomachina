# Runtime footprint decision and focused countertrials

> **Later decision, 23 September:** bundled orchestration workers may restart or roll out automatically to load new factory definitions if existing runs retain their pinned behavior and independent A2A services are unaffected. The [Zigflow reassessment](../tools/spikes/2026-09-23/zigflow-reassessment/result.md) removes worker refresh as a hard exclusion but retains its activation and version-retirement costs. The [fresh engine arbitration](engine-reassessment-2026-09-23.md) chooses Temporal's stable interpreter for development, with Effect second. The measurements and decisions below remain historical.

22 September 2026 · Architecture decision after the bounded S0–S4 probes · **No product engine selected**

**Later round-two evidence:** [six executable candidate trials](../tools/spikes/2026-09-22/round-two/result.md) now test Dagu, core Strands Graph, Effect, Temporal, Restate and Hatchet under a common narrow publication/restart question. One stable interpreter removed the earlier Zigflow-specific Temporal worker-refresh obstacle; Effect and Graph advance to a common product-shaped proof. The measurements below describe the *first* countertrial wave and remain historical evidence, not the current candidate judgment. No complete or matched Strands+A2A installation has been measured.

## Decision

Do not launch a separate Kestra and PostgreSQL pair for every factory-capable Strands harness. That topology is too heavy for the intended local, multi-agent experience. A **single automatically managed local engine and store per Exomachina installation** remains a conditional Kestra option: one install/start command must bring them up, multiple harness instances may use them, and every instance still has its own stable identity and durable state. The engine is not an externally provisioned service or a shared conversation.

Kestra remains the **observed behavioral development baseline**, because its S1–S4 factory probes passed. It is no longer the presumed product runtime. Continue using those fixtures to compare behavior; do not expand Kestra-specific product implementation until its shared-helper footprint and lifecycle fit an agreed resource envelope. No numerical idle-memory ceiling or target machine has yet been agreed, so this is a topology decision and a measurement gate, not a claim that every Kestra installation fails a fixed limit.

The [S0 measurement](../tools/spikes/2026-09-22/s0/kestra/result.md#observed-footprint-and-limits) was **about 650 MiB RSS for one warm-idle Kestra JVM alone**, after small flows, with `-Xmx1g` and four worker threads. PostgreSQL and Strands were additional or unmeasured; peak and sustained-load memory were not measured. The [609 MiB host-local bundle](../tools/spikes/2026-09-22/s0/kestra/package/result.md) is **disk size**, including 66 MiB of state, not RAM. Kestra's [standalone guidance](https://kestra.io/docs/administrator-guide/requirements) calls for at least 4 GiB of host RAM and two vCPUs; that is vendor host sizing, not a measured idle RSS. Multiple independent JVMs would repeat most private heap/runtime overhead, although RSS is not an exact linear physical-memory forecast because processes can share pages. One shared local helper pays its baseline once; its incremental workload cost remains unmeasured.

Sharing is not free glue. The package needs a single lifecycle owner, readiness and restart handling, collision-free ports and instance identifiers, durable instance-to-run mappings, and backup/upgrade ownership. Every direct engine path must remain behind Exomachina's authorization Interface; Kestra OSS [Basic Auth and namespaces](https://kestra.io/docs/oss-vs-paid) do not provide per-harness authorization. The first deployment still serves one organization; future customer isolation is a separate qualification. These responsibilities belong inside a small Factory Module and engine Adapter, not a second scheduler or universal workflow DSL.

## Bounded countertrials — observed results

The three focused countertrials ran on the same Mac with isolated state. They were **not a controlled, serial comparison**: their processes overlapped, their workloads differed, and none included the complete Strands+A2A product. Do not compare summed RSS directly with a macOS physical-footprint figure, or treat these as whole-installation resource scores.

| Candidate | What the pinned trial established | Decisive remaining cost |
| --- | --- | --- |
| **[Dagu Community v2.17.0](../tools/spikes/2026-09-22/countertrials/dagu/result.md)** | One local server/scheduler process with file-backed state; 105.6 MiB fresh idle and 120.8 MiB warm server RSS. Native nested approval remained waiting across restart; a two-request approval race made one delivery in this fixture. Two overlapping active runs spawned separate runners and the seven-process set measured 156 MB macOS physical footprint. | A paused parent invoked a **changed child definition** after resume; publication must pin the transitive dependency closure. Exact GPL-compliant packaging, product authorization, independent-root coordination and remote recovery remain open. |
| **[Temporal Server v1.32.0 + Zigflow v0.15.2](../tools/spikes/2026-09-22/countertrials/temporal/result.md)** | A non-development server with PostgreSQL persistence/visibility ran without Docker. Old and new pinned Zigflow workers kept their respective workflow definitions; six overlapping HTTP Activities completed. Idle server, PostgreSQL and one worker measured 321.2 MiB macOS physical footprint, excluding Strands/UI. | A new Zigflow definition added to a running worker still failed until worker refresh. Retaining versioned workers adds process cost; a stable interpreter would move authoring semantics and publication ownership into Exomachina. |
| **[Core Strands Graph 1.57.0](../tools/spikes/2026-09-22/countertrials/strands_graph/result.md)** | Two small Python harness processes each resumed pinned v1/v2 graphs after SIGKILL using SDK snapshots and interrupts; warm paused RSS was 71.9 MiB **per minimal process**, excluding A2A and real agents. | The trial-owned document publisher/reconstructor supplied versioning. Two unfenced processes resumed the **same run** and both executed delivery, so fenced run ownership and external-effect deduplication are product work. |

The trials strengthen **Dagu as a lightweight declarative challenger** and show that core Strands Graph can avoid a separate engine process for simple graphs. They do not supersede Kestra's broader S1–S4 behavioral evidence or select a product engine. Temporal's publication blocker is the assessed **Zigflow layer**, not Temporal's execution engine. Strands Graph's duplicate-delivery result is a real missing ownership boundary, not proof that snapshots are useless. A shared Kestra helper and complete Dagu/Strands installations still need a serial common workload before resource ranking or final selection.

**Effect Workflow + Cluster was omitted from that first countertrial set.** The [subsequent candidate screen](effect-workflow-evaluation-2026-09-22.md) identifies a plausible third topology: one bundled Node helper with a SQL-backed single-node runner and local SQLite, shared by multiple Strands harness instances. Its MIT-licensed runtime primitives may reduce the execution infrastructure burden. A [pinned v3 local trial](../tools/spikes/2026-09-22/countertrials/effect_workflow/result.md) observed a persisted approval wait completing after process kill/restart and about 185 MiB warm-idle RSS for the **helper alone**. No whole-install resource or governed factory-publication result has been established. Its TypeScript workflow definitions would require Exomachina to own a managed factory-document layer or prove an alternative versioned registration path. Effect remains unscored; do not infer it is lighter than Dagu or a substitute for a native document DSL.

## Original trial protocol and remaining gates

The bounded Dagu, Temporal and core Strands Graph trials asked the package/resource and publication questions below, using the observed Kestra package as a reference. The Strands trial was narrower: it tested whether the harness's Graph facilities avoid a separate engine without creating a bespoke one. These were decision screens, not full E01–E10 or production qualification. The [Dagu screen](exomachina-candidate-screening.json) and [Temporal authoring evaluation](temporal-authoring-evaluation.md) retain their broader open gates. Stop future candidate-specific integration early if product rights, the required publication model, or the one-command local topology fails.

| Candidate | Exact trial topology | First decisive question |
| --- | --- | --- |
| **Kestra OSS v2.0.3 reference** | One bundled local Kestra JVM and PostgreSQL pair shared by two harness instances. | Does the **whole installation**, including Strands and storage, meet the agreed idle/paused/active envelope? Can either harness restart or exit without stopping the other's work, while direct engine access stays protected? |
| **Dagu Community** | Pin a released, separately operated local server using its documented file-backed state; include any scheduler/coordinator/worker processes actually needed for the selected mode. | Is the real package materially lighter, permitted for the intended distribution, and capable of the required nested wait/result/recovery contract without replacing its scheduler? A small binary is not a RAM result. |
| **Temporal Server + authoring worker** | Pin a **non-development** self-hosted Temporal Server binary with PostgreSQL persistence/visibility, one Zigflow or other selected authoring worker, and the Strands harness; include UI only if the product requires it. | Does this complete topology improve the resource/operation tradeoff **and** preserve agent-authored publication without refreshing workers? The previous SQLite `start-dev` probe cannot answer production footprint. |
| **Core Strands Graph** | Use the pinned Python SDK inside the existing harness with its documented graph checkpoints and interrupts; include whatever durable session store the tested topology needs. Do not substitute the separate Strands Tools graph/workflow utilities for the SDK. | Can a versioned, approved factory document build a graph and publish v2 without harness refresh while an interrupted v1 stays bound, with correct concurrent ownership and remote recovery, **without** Exomachina taking on a large interpreter/scheduler? |

Temporal documents a [Docker-free server-binary deployment](https://docs.temporal.io/self-hosted-guide/deployment) and [PostgreSQL visibility](https://docs.temporal.io/self-hosted-guide/visibility). Its [embedded SQLite mode is for development and testing](https://docs.temporal.io/self-hosted-guide/embedded-server). The measured Zigflow v0.15.2 trial found that a new definition required worker refresh, an unversioned waiting execution could adopt changed behavior, and explicit pinned worker deployments preserved the tested old/new behavior. **That is a limitation of the assessed Zigflow authoring layer, not Temporal's durable execution engine.** A stable interpreter could accept definitions as data, but Exomachina would own its semantics, validation, publication, and compatibility unless a maintained permitted layer is proven. If worker rollout for every new factory remains unacceptable and no such layer passes, stop the Temporal trial before A2A integration; a lower server RSS alone would not make it fit.

The current [Strands Graph SDK](https://strandsagents.com/docs/user-guide/sdk/multi-agent/graph/) documents nested graphs, A2A nodes, conditional edges and Python checkpoint state across interrupt/resume. [Session management](https://strandsagents.com/docs/user-guide/sdk/agents/session-management/) also documents per-node snapshots, but no distributed session lock. The Python Graph's incoming edges default to **OR**, so a required all-branch review join needs an explicit condition. The SDK [Workflow pattern](https://strandsagents.com/docs/user-guide/sdk/multi-agent/workflow/) is code-defined orchestration, not a managed document runtime. Current Strands Tools [graph](https://github.com/strands-agents/tools/blob/main/src/strands_tools/graph.py) stores runtime graphs in memory, while its [workflow tool](https://github.com/strands-agents/tools/blob/main/src/strands_tools/workflow.py) does not implement pause/resume; neither clears governed durable publication. The pinned Graph trial confirmed both checkpoint recovery and the unfenced-owner duplicate-delivery risk. Product-level publication, remote reconciliation and fenced ownership remain its simplicity test.

## Common measurement and stop rule

1. Pin candidate artifact/commit, license and intended distribution, exact processes and storage mode. Reject development-only modes as product comparisons. Record the one-command, no-Docker startup path and what the package owns at upgrade or shutdown.
2. On the same host and comparable fixture, record unpacked package and initialized-state disk use, cold and warm startup, **per-process RSS plus a non-double-counted whole-install memory measure**, CPU, and the process count. Measure after startup, after the same durable paused factory, and during a small overlapping workload. Include PostgreSQL, authoring workers, Strands harnesses and any required UI; state clearly when a process is optional. Compare one and at least two harness instances, both separate and shared-engine topologies only where they are actually supported.
3. Restart the shared helper and either harness independently. Verify each harness's identity, pending work and accepted artifacts survive; one harness exit must not terminate another's work. Record port, store and authorization ownership rather than inferring isolation from a namespace.
4. Prove a new agent-authored composition and a waiting v1 run while v2 publishes. For Temporal, make the Zigflow worker-rollout choice explicit before deeper testing; if a stable interpreter is proposed, count its owned language and release machinery. For Dagu, test native sub-DAG approval and separate-root factory composition rather than assuming the root-only typed `human.task` rule forbids all nested gates. For Strands Graph, count the document-to-GraphBuilder publisher, approved node/condition vocabulary, revision pinning and restart reconstruction as owned implementation; fail the simplicity gate if that becomes a second workflow engine.
5. Only candidates that pass those gates proceed to one common exact-artifact acceptance and lost-acknowledgement/recovery slice through the Strands Factory Interface. Full E01–E10, Engineering cases, load, backup and upgrade qualification follow a product selection.

Set the target platforms, acceptable **total** warm-idle and active memory, startup, disk and operating burden before using these measurements for a selection score. Until then, record measured values and uncertainty rather than inventing a pass threshold. Keep the 65-feature matrix unchanged: it measures documented capability. Update the separate [selection judgment](exomachina-selection-judgment.json) as packaging and resource evidence arrives.
