**My preferred option is Conductor OSS v3.32.4, built from its Apache-2.0 source, with PostgreSQL for persistence, queues, indexing and distributed locks. Confidence: moderate.** This is my preferred qualification target, not approval for production adoption. It includes the OSS server/UI, Exomachina’s publication and authority gateway, a reusable remote-service Adapter, and artifact storage. PostgreSQL locking, immutable dependency binding, hostile authoring and recovery races remain adoption gates. No candidate has passed every required gate. The assessed [release](https://github.com/conductor-oss/conductor/releases/tag/v3.32.4) and [license](https://github.com/conductor-oss/conductor/blob/v3.32.4/LICENSE) are distinct from Orkes products and their entitlements.

My reason is architectural: Exomachina is principally a product for publishing and executing compositions of independent services. Conductor already treats a process definition as runtime data and external work as individually tracked tasks. That combination offers useful Depth behind an existing Interface without introducing another language interpreter that Exomachina must maintain. I do not propose relaxing the requirement that compositions of existing capabilities publish without worker deployments or refreshes.

**Why I prefer this fit.** Conductor separates workflow definitions, executions and worker implementations. Definitions contain versioned graphs; the server interprets their ordering and data flow, while workers poll tasks and report results. Its existing metadata publication surface lets an agent or customer submit a new composition of installed task types without changing those workers. This is precisely the separation between factory and capability catalogs that Exomachina needs, although neither engine metadata nor worker registration replaces the product’s public capability contracts. [Definition model](https://conductor-oss.github.io/conductor/documentation/configuration/workflowdef/index.html), [execution architecture](https://conductor-oss.github.io/conductor/devguide/architecture/index.html).

The task lifecycle matters more than the AI integration catalog. A remote research assignment can remain outstanding under a stable engine task identity while other branches progress. A `HUMAN` task is actually an externally completed gate: an authorized agent Director can complete it as readily as a person. HTTP tasks can also remain `IN_PROGRESS` after a successful submission using `asyncComplete`. These are existing continuation mechanisms, rather than a requirement to keep a request open. They still need authenticated correlation and safe completion handling. [Human task](https://conductor-oss.github.io/conductor/documentation/configuration/workflowdef/systemtasks/human-task.html), [released HTTP implementation](https://github.com/conductor-oss/conductor/blob/v3.32.4/http-task/src/main/java/com/netflix/conductor/tasks/http/HttpTask.java).

Factories can use native subworkflows internally while exposing the same factory through a public service Interface. Parallel research, synthesis, independent review, bounded repair and a Director decision can remain visible in one engine-owned execution tree. The released subworkflow implementation includes deterministic child identities and cancellation handling. That is source evidence for useful recovery machinery, not proof that every race is safe. [Operators](https://conductor-oss.github.io/conductor/documentation/configuration/workflowdef/operators/index.html), [v3.32.4 subworkflow source](https://github.com/conductor-oss/conductor/blob/v3.32.4/core/src/main/java/com/netflix/conductor/core/execution/tasks/SubWorkflow.java).

Version numbers are insufficient. Exomachina must reject mutation of published versions, pin every child and capability revision, and preserve policy and execution-profile bindings. Conductor’s mapper retains a workflow definition on the execution but can resolve an unspecified subworkflow version from current metadata. Therefore publication must close over explicit dependencies; dynamic selection must stay inside that approved set. This is a catalog policy over the existing engine, not a second scheduler. [Released metadata mapper](https://github.com/conductor-oss/conductor/blob/v3.32.4/core/src/main/java/com/netflix/conductor/core/metadata/MetadataMapperService.java).

The production path is real and free: shared durable storage, task queues and distributed locking are documented OSS facilities. PostgreSQL can provide all four persistence/queue/index/lock functions, reducing deployment dependencies. The docs explicitly require workload benchmarking, however, and the general deployment guide emphasizes other lock providers. I would qualify the PostgreSQL configuration rather than declare it production-safe from documentation. If necessary, the documented Apache ZooKeeper lock provider is a permitted replacement, at the cost of another operated subsystem. SQLite quickstart success would not settle this. [PostgreSQL configuration](https://conductor-oss.github.io/conductor/documentation/advanced/postgresql.html), [production deployment](https://github.com/conductor-oss/conductor/blob/v3.32.4/docs/devguide/running/deploy.md).

**What Exomachina actually owns.** Across all candidates, the unavoidable work is the public product contract:

- Separate capability and factory catalogs; schemas, immutable revisions and dependency bindings; authorized publication using the engine’s existing definition language.
- Acceptance records identifying the exact artifact revision, reviewer independence, repair attempts, and the Director authority that resolved a wait.
- Admission and atomic budget reservations across concurrent branches; scoped credentials; customer isolation; protected evaluators and publication privileges.
- A remote-service Adapter preserving task IDs, continuation, artifact references, cancellation and restart reconciliation. Lost acceptance requires service-supported deduplication/discovery or an honest unknown outcome. Engine retries cannot manufacture exactly-once external effects.

I would initially implement these as a small product control Module plus a separately runnable Adapter/reconciler, not one microservice per responsibility. Their durable records can use separate PostgreSQL schemas; artifacts belong in a retained object store. The engine remains responsible for graph transitions, scheduling and execution history. Capability providers retain their private harnesses and models. A new capability implementation can require deployment; rearranging existing capabilities cannot.

Conductor-specific work is narrower: validate an approved JSON task profile, publish through metadata operations, translate task events and expose safe product operations. Customers do not receive unrestricted engine credentials. An OIDC gateway with product authorization, constrained task types and destinations, provider-scoped secrets, and append-only decision records can replace paid identity/governance facilities without importing proprietary code. This is feasible engineering, not an assertion that putting authentication in front of the native UI creates tenant isolation. Operational ownership includes server/database upgrades, backups, retention, monitoring and lock qualification. Source-license permission also does not clear every supplied image: build and inventory a pinned OSS artifact and its dependencies before redistribution.

**Temporal is the strongest architectural counterargument.** The exact alternative assessed is self-hosted Temporal Server v1.32.0 plus upstream Zigflow v0.15.2, production PostgreSQL persistence/visibility, Temporal UI and retained versioned Zigflow workers. Temporal has the strongest execution-recovery model in this comparison: event history is the recovery mechanism, durable messaging is fundamental, and worker versioning makes long-lived implementation compatibility explicit. Production self-hosting is documented; its MIT core and Zigflow’s Apache core do not require purchasing Cloud. This should carry substantial weight even when a feature checklist favors another engine. [Temporal deployment](https://docs.temporal.io/self-hosted-guide/deployment), [event history](https://docs.temporal.io/workflow-execution/event), [worker versioning](https://docs.temporal.io/worker-versioning), [Temporal license](https://github.com/temporalio/temporal/blob/v1.32.0/LICENSE), [Zigflow license](https://github.com/zigflow/zigflow/blob/v0.15.2/LICENSE).

I nevertheless would not select that stack under the present publication requirement. Zigflow compiles and registers definitions when workers start; `--watch` reloads workers and is documented for development. Immutable worker rollouts are a legitimate architecture, but accepting them for every factory publication would change the requirement explicitly. A generic dynamic interpreter could preserve publication without refresh while reusing Temporal’s scheduler, timers, history and recovery. The additional ownership would be definition semantics, validation, dispatch, publication, immutable binding and interpreter compatibility—not rebuilding Temporal itself. That remains substantially more engine-specific responsibility than a remote protocol Adapter. [Zigflow execution model](https://zigflow.dev/docs/concepts/how-zigflow-runs/), [run command](https://zigflow.dev/docs/cli/commands/zigflow_run/).

Nor should the full Temporal SDK be credited automatically to Zigflow. The local source audit reports nested input/version-binding limitations and sequential runtime iteration despite fixed parallel forks, grounded in the released [child invocation](https://github.com/zigflow/zigflow/blob/v0.15.2/pkg/zigflow/tasks/task_builder_run.go) and [iteration implementations](https://github.com/zigflow/zigflow/blob/v0.15.2/pkg/zigflow/tasks/task_builder_for.go). Those are authoring-layer concerns, not Temporal weaknesses. Temporal’s history debugger and replay discipline would be especially valuable if incident recovery becomes highly interactive; conversely we would operate both Temporal and an independently evolving authoring layer, retain compatible workers, and manage history limits. If publication becomes release-managed by an explicit product decision, I would reconsider Temporal seriously rather than merely move it up a score table.

**Kestra OSS v2.0.3 is the closest alternative under unchanged requirements.** It has native YAML/API publication, a strong visual authoring and operations surface, revisions, subflows, HTTP integrations and durable pauses. Current documentation explicitly supports distributed HA with the OSS JDBC backend; calling it development-only would be wrong. Its Apache-2.0 core permits a commercial or open-source product, subject to ordinary obligations. [Release/license](https://github.com/kestra-io/kestra/blob/v2.0.3/LICENSE), [architecture](https://kestra.io/docs/architecture), [HA](https://kestra.io/docs/administrator-guide/high-availability).

The concrete difference is task completion. Conductor’s external worker/task update protocol makes each remote assignment an addressable outstanding engine task. Kestra can feasibly implement equivalent product behavior with HTTP submission, a subflow containing `Pause` and typed `onResume` inputs, bounded status polling, or a reusable custom plugin. Pause explicitly suspends flow scheduling and resumes through an execution operation. Parallel independently waiting assignments therefore need careful subflow organization or plugin behavior. This is additional mapping between service tasks and execution pauses, not missing durable orchestration. [Kestra Pause](https://kestra.io/plugins/core/flow/io.kestra.plugin.core.flow.pause), [HTTP Request](https://kestra.io/plugins/core/http/io.kestra.plugin.core.http.request), [Subflow](https://kestra.io/plugins/core/flow/io.kestra.plugin.core.flow.subflow).

The accepted generic A2A Adapter substantially narrows this difference. It needs remote correlation and reconciliation with either engine; Conductor does not eliminate that store or its failure cases. My remaining preference is that its existing task protocol matches the dominant workload directly, with less per-definition ceremony and less reason to maintain an engine plugin. It is a moderate preference. Kestra’s integrated editing/debugging experience could outweigh it if the reference workflow proves equally simple to operate.

Kestra’s native tenant/RBAC/secret integrations are edition-sensitive. A private engine behind the same product gateway, provider-owned secrets and appropriately isolated deployments offers a free permitted path. That limitation also prevents Conductor from claiming an unfair governance advantage. Kestra subflows default to the latest revision, so explicit revision binding is required; its worker/plugin upgrades also need compatibility management. Its richer plugin catalog has more value if Exomachina starts doing substantial work inside the engine, rather than delegating to independently deployed services. [Edition comparison](https://kestra.io/docs/oss-vs-paid), [subflow revision semantics](https://kestra.io/plugins/core/flow/io.kestra.plugin.core.flow.subflow).

**Argo Workflows v4.1.4** would be compelling with an existing Kubernetes operating team and substantial containerized research or evaluation workloads. WorkflowTemplates provide reusable declarative publication, suspension supports waits, and HTTP templates mean it need not launch a fresh container for every service call. Kubernetes permissions and resource isolation are valuable. Its Apache core is product-compatible. [Templates](https://argo-workflows.readthedocs.io/en/latest/workflow-templates/), [HTTP templates](https://argo-workflows.readthedocs.io/en/latest/http-template/), [license](https://github.com/argoproj/argo-workflows/blob/v4.1.4/LICENSE).

For this service-composition product I would avoid making Kubernetes workflow resources the primary authoring abstraction. We would operate the controller/server and cluster, artifact storage and potentially SQL archive/offload, while still implementing service continuation and acceptance policy. Debugging is excellent for workflow nodes and pods but remote task state still needs correlation. Immutable template identities and retained dependencies require publication discipline. Argo is mature and recoverable, not incapable; its operational and conceptual investment pays back best when container execution is central. Archive storage also excludes pod logs unless separately configured. [Archive](https://argoproj.github.io/argo-workflows/workflow-archive/).

**Dagu Community v2.17.0** has the most attractive small deployment: a binary, file-backed state, YAML, UI, human tasks and distributed workers. It deserves a real prototype if footprint dominates. Workers communicate status, logs and artifacts through the coordinator, making that coordinator/storage arrangement an important recovery dependency. Its documented automatic DAG retry window also needs explicit treatment for long-lived incidents. [Worker deployment](https://docs.dagu.sh/server-admin/distributed/workers/shared-nothing), [durable execution](https://docs.dagu.sh/writing-workflows/durable-execution).

I prefer Conductor’s service/task model and database-backed production operating pattern for the broader product. Dagu can expose factories as independent roots through an Adapter; that is feasible, but cross-root result delivery, cancellation and budgets remain owned coordination. The local screening records this honestly as untested. GPL permits commercial operation and compliant distribution: it is not an internal-use-only restriction. Separately operated Dagu is materially different from distributing a proprietary combined Go binary; the latter is not cleared by its public embedding terms. Community’s paid native SSO/RBAC/audit facilities would require the same external product controls. [Licensing](https://github.com/dagucloud/dagu/blob/v2.17.0/LICENSING.md), [community/paid capabilities](https://github.com/dagucloud/dagu/blob/v2.17.0/README.md).

A later factual cross-check surfaced **Tracecat 1.0.1**, a maintained Temporal application with dynamic definition publication. It potentially solves Zigflow’s publication problem, but brings a larger application platform and unresolved artifact licensing: its release README excludes both EE code and EE-gating code from the AGPL grant and restricts production/redistribution of those exceptions. I would require an exact permitted free artifact before considering it a replacement. AGPL itself is not the disqualifier. [Release terms](https://github.com/TracecatHQ/tracecat/blob/1.0.1/README.md). LangGraph stays excluded; n8n Community and distributed Windmill Community remain outside this selection. Strands remains a possible worker implementation.

**Required Engineering is part of the design.** Production, Quality and Engineering can each have one supervisor coordinating workers under the Director. Engineering runs two recurring factory families: incident diagnosis/recovery and continuous improvement. Recovery must reconcile existing remote effects before replacement work, use a fenced recovery owner, retain accepted artifacts, bound repairs and escalate when authority or outcomes are uncertain. Engine retries support this; they do not define safe self-healing. Infrastructure monitoring and database/host recovery also need an external operational path when the engine itself is unavailable.

Improvement consumes incident and quality evidence, proposes a new immutable factory version, runs protected baseline/candidate evaluations, and publishes only through the authorized path. Quality owns acceptance and evaluation; Engineering cannot edit its own passing standard. Optional autoresearch is a bounded candidate generator inside this system, not a substitute for ongoing Engineering. Conductor’s ordinary workflows and external services can express this organization without extra management layers. Every alternative needs essentially the same domain policy; Temporal may handle complicated recovery conversations more elegantly, while Kestra and Argo offer useful experiment operations.

**The strongest objection to my choice is ownership after failures.** Conductor’s convenient publication does not prove that its current lock, retry, callback and cancellation interactions are easier to trust than Temporal’s history-based model. I have not run the selected Conductor topology. All five candidates have current releases, but release freshness is maintenance evidence, not workload maturity. Temporal’s server maturity does not automatically transfer to Zigflow, and Conductor’s established orchestration design does not automatically qualify newer modules. Conductor’s task definitions and JSON expressions also create migration cost. Keeping service contracts and artifact identities independent helps, but active histories cannot simply migrate to another engine: drain them or maintain the old runtime. The same applies to Temporal/Zigflow, Kestra, Argo and Dagu; an open DSL does not make execution semantics portable.

I would reverse or withhold this recommendation on concrete evidence:

- Publish two different compositions without refreshing workers; pause v1, publish v2, alter aliases, restart and resume. Any unapproved dependency drift blocks adoption.
- Race task completion, timeout, cancellation and two recovery owners; lose submission responses and crash after remote acceptance. Duplicate effects, stale acceptance or falsely certain outcomes block adoption.
- Fail over the database and kill engine/Adapter processes during nested waits and repair. Test lock expiry, queue recovery, backups and realistic concurrent load. PostgreSQL lock failure may change the topology; irreparable engine behavior changes the choice.
- Attempt cross-customer reads, arbitrary destinations, review bypass and concurrent overspending. The gateway must enforce these without paid-only dependencies.
- Run identical Engineering/Quality cases on Kestra. If it needs no more owned coordination and is materially easier to debug, prefer it. Reconsider Temporal if a maintained, permitted publication layer passes these tests, or the user explicitly accepts worker lifecycle changes for publication.
