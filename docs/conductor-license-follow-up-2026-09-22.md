# Conductor package-rights follow-up — 22 September 2026

**Finding:** the stock Conductor v3.32.4 server package has a real product-rights question, but the restricted queue library is not required for the PostgreSQL factory path. A source-built server without that library compiled, executed a workflow, and retained the result across a server restart. Conductor remains a technical candidate; this finding does not clear the stock package or qualify the modified build for distribution.

## License evidence

The published [server POM](https://repo.maven.apache.org/maven2/org/conductoross/conductor-server/3.32.4/conductor-server-3.32.4.pom) declares `io.orkes.queues:orkes-conductor-queues:2.0.0.rc3`, and that JAR is inside the published boot JAR. Its [POM](https://repo.maven.apache.org/maven2/io/orkes/queues/orkes-conductor-queues/2.0.0.rc3/orkes-conductor-queues-2.0.0.rc3.pom) identifies the [Orkes Community License](https://github.com/orkes-io/licenses/blob/14cd5d6b0619399c205a022cc7b512734ea51911/community/LICENSE.txt). Article 2.1 includes internal use and binary/source distribution grants, conditioned on Article 3. Article 3.3 restricts third-party service and competitive-product provision/development. A customer-local, one-organization helper weakens the hosted-service concern, but Exomachina's customer-authored orchestration overlaps [Orkes's workflow offering](https://www.orkes.io/content/agentic-workflow-engine). That overlap is a genuine unresolved rights question for the stock package, not a conclusion that every commercial use is prohibited. Conductor's [Apache 2.0 source license](https://github.com/conductor-oss/conductor/blob/v3.32.4/LICENSE) does not relicense the nested Orkes JAR. [Discussion #108](https://github.com/orgs/conductor-oss/discussions/108) and [issue #139](https://github.com/conductor-oss/conductor/issues/139) document a similar public concern; neither grants Exomachina rights.

## Independent runtime checks

The investigation used pinned source commit `088de237a185caaeb669035a6d75de65d36cab5a` from tag `v3.32.4`. In an isolated scratch clone, removing four declarations from [`server/build.gradle`](https://github.com/conductor-oss/conductor/blob/v3.32.4/server/build.gradle) removed the direct Orkes queue JAR, Redis persistence, Redis scheduler persistence, and the workflow event listener. Gradle 8.14.3 on JDK 21 resolved `:conductor-server:runtimeClasspath` without the Orkes queue dependency and built `:conductor-server:bootJar` successfully. The resulting JAR (SHA-256 `8d1d0ceaf4b02db3342a58f051a96e1ef05c23886aacec2f435bb483713aad50`) contains PostgreSQL persistence and scheduler JARs, with no nested Orkes queue, Redis persistence, or workflow event listener JAR. Its filename says `3.30.2-SNAPSHOT` because the pinned source's `gradle.properties` retains that version; the source commit identifies this experiment.

The source-built server started against isolated PostgreSQL 16.15 with database, queue, indexing, and lock set to PostgreSQL. It accepted the repository's `SET_VARIABLE` workflow fixture, completed a run with `variables.var=source-postgres-ok`, then returned that same completed execution after a server restart. A separate check removed only the Orkes queue JAR from a copy of the published boot JAR; that copy started with PostgreSQL database/queue/indexing, completed the fixture with `variables.var=postgres-ok`, and returned the result after restart. The modified published JAR is a diagnostic runtime check, not a proposed release procedure. Both trials used temporary local PostgreSQL state and narrow example workflows, not product credentials or production security settings.

The dependency is genuinely used by the Redis path: [`BaseRedisQueueDAO`](https://github.com/conductor-oss/conductor/blob/v3.32.4/redis-persistence/src/main/java/io/orkes/conductor/mq/dao/BaseRedisQueueDAO.java) imports classes from the restricted JAR. PostgreSQL has its own [`PostgresQueueDAO`](https://github.com/conductor-oss/conductor/blob/v3.32.4/postgres-persistence/src/main/java/com/netflix/conductor/postgres/dao/PostgresQueueDAO.java). The four-line source variant loses Redis database/queue and Redis scheduler storage, plus workflow event listener features such as archiving and Kafka/Conductor-queue status publication. The current Factory contract does not require those listener integrations explicitly, but its Conductor-specific implementation has not been tested. For a PostgreSQL-only installation, set `management.health.elasticsearch.enabled=false` or the unused Elasticsearch health contributor reports `DOWN` despite a working PostgreSQL runtime.

## Decision boundary

The original S0 conclusion is a **stock-artifact gate**, not a **Conductor engine dealbreaker**. To adopt Conductor, own a reproducible patched source build, audit every bundled dependency and notice, verify the omitted integrations are unnecessary or replaceable, and run the previously planned S0–S4 behavioral and one-install tests against that exact build. Specific written Orkes rights are the other path for the stock package. Kestra remains the provisional development baseline because its broader factory behaviors were tested, not because Conductor lacks a technically workable PostgreSQL assembly.

The later [resource/topology decision](runtime-resource-decision-2026-09-22.md) preserves that behavioral evidence but rejects a Kestra/database pair per harness as the default. Conductor's source variant has no comparable whole-install footprint measurement either; its JVM and packaging cost remain open.

One separate artifact-integrity observation remains unresolved: the downloaded stock boot JAR matched Maven's `.md5` and `.sha1` sidecars but not its `.sha256` sidecar. The source-build result does not depend on that published digest; any release pipeline should pin and verify its own artifact hashes.
