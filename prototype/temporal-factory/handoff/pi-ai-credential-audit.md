# pi-ai 0.87.1 credential-path audit

Read-only static audit of the installed `@earendil-works/pi-ai` in `broker/node_modules/`, compared with `broker/exo-model.mjs` as present during this audit. Paths and line numbers below are relative to `prototype/temporal-factory/`. No login, token-file read, or OpenAI request was made.

## Credential and environment paths

1. `createModels()` itself does not discover credentials or files. Its default credential and model stores are in memory; absent an injected context, it installs `defaultProviderAuthContext()` (`broker/node_modules/@earendil-works/pi-ai/dist/models.js:31-35`, `broker/node_modules/@earendil-works/pi-ai/dist/auth/credential-store.js:2-9`, `broker/node_modules/@earendil-works/pi-ai/dist/models-store.js:1-15`). The default context reads `process.env[name]`; its file probe expands `~` with `os.homedir()` and calls `fs.access`, without reading file contents (`broker/node_modules/@earendil-works/pi-ai/dist/auth/context.js:11-40`). `getAuth()` passes the injected context and credential store to `resolveProviderAuth()` (`broker/node_modules/@earendil-works/pi-ai/dist/models.js:276-291`). `checkAuth()`/`getAvailable()` and model-catalog `refresh()` also read the injected store and may invoke provider API-key resolution (`broker/node_modules/@earendil-works/pi-ai/dist/models.js:134-163,190-217,223-274`). Explicit `getAuth(provider, {env, apiKey})` or stream options can supply values independently of the empty context: `env` overlays the context; `apiKey` can select API-key auth for providers that offer it (`broker/node_modules/@earendil-works/pi-ai/dist/auth/resolve.js:30-60`, `broker/node_modules/@earendil-works/pi-ai/dist/models.js:359-379`).

2. The registered `openai-codex` provider offers **OAuth only**, with a static model catalog; it has no API-key resolver or model-catalog network refresh (`broker/node_modules/@earendil-works/pi-ai/dist/providers/openai-codex.js:6-20`, `broker/node_modules/@earendil-works/pi-ai/dist/models.js:461-495`). Therefore `OPENAI_API_KEY` is not a fallback for this provider, even with the default context. `OPENAI_API_KEY` belongs to the separate `openai` API-billed provider (`broker/node_modules/@earendil-works/pi-ai/dist/providers/openai.js:6-12`); that provider's standard resolver asks `ctx.env()` (`broker/node_modules/@earendil-works/pi-ai/dist/auth/helpers.js:16-28`). `Models.refresh()` is a model-catalog operation and does not refresh Codex OAuth for this static provider (`broker/node_modules/@earendil-works/pi-ai/dist/models.js:134-143`, `broker/node_modules/@earendil-works/pi-ai/dist/providers/openai-codex.js:6-20`).

3. Codex `getAuth()` first reads the **injected credential store**. A stored OAuth credential owns the provider, and a token with less than five minutes of validity is refreshed under `credentials.modify()` before `oauth.toAuth()` returns its access token. If no credential is stored, Codex has no ambient API-key resolver (`broker/node_modules/@earendil-works/pi-ai/dist/auth/resolve.js:40-55,62-115`; `broker/node_modules/@earendil-works/pi-ai/dist/auth/oauth/openai-codex.js:422-449`). `Models.login()` invokes the provider's OAuth login and writes its result through the injected store; `Models.logout()` calls that store's delete method (`broker/node_modules/@earendil-works/pi-ai/dist/models.js:293-350`). The package itself has no `~/.codex/auth.json` or `~/.pi/**` import in these paths. An injected store may read any location its host implementation chooses; the empty `authContext` does not constrain that store. The separate **pi-ai CLI** explicitly reads and writes `auth.json` relative to its working directory, but the broker imports package APIs, not `dist/cli.js` (`broker/node_modules/@earendil-works/pi-ai/dist/cli.js:1-21,37-67`; `broker/exo-model.mjs:102-107`).

4. The OAuth flow bypasses `authContext` for `PI_OAUTH_CALLBACK_HOST`: browser login resolves that name through `getProviderEnvValue()` for its callback listener (`broker/node_modules/@earendil-works/pi-ai/dist/auth/oauth/openai-codex.js:36-37,292-295,354-356`; `broker/node_modules/@earendil-works/pi-ai/dist/utils/provider-env.js:35-42`). `getProviderEnvValue()` reads `process.env` and has a Bun-only fallback that reads `/proc/self/environ` when the process environment is empty (`broker/node_modules/@earendil-works/pi-ai/dist/utils/provider-env.js:12-42`). This direct read is **not** closed by `{env: async()=>undefined, fileExists: async()=>false}`. It affects the local callback bind address, not the credential source. Device login, token exchange, and token refresh have no other direct pi-ai environment/file read in their shown paths (`broker/node_modules/@earendil-works/pi-ai/dist/auth/oauth/openai-codex.js:112-228,342-352,422-449`).

5. The Codex stream gets its bearer from `options.apiKey`, builds its request, and performs SSE with `options.fetch ?? globalThis.fetch` (`broker/node_modules/@earendil-works/pi-ai/dist/api/openai-codex-responses.js:143-180,255-272`). Its default `transport: "auto"` can try WebSocket first; in Bun, the WebSocket proxy helper reads `no_proxy`, scheme-specific proxy variables, and `all_proxy` through `getProviderEnvValue()` or `options.env` (`broker/node_modules/@earendil-works/pi-ai/dist/api/openai-codex-responses.js:184-203,708-736`; `broker/node_modules/@earendil-works/pi-ai/dist/utils/node-http-proxy.js:10-17,62-64,98-113`). The broker forces SSE, so that pi-ai WebSocket proxy path is not reached (`broker/exo-model.mjs:157-160`). The SSE path itself has no pi-ai `process.env` or filesystem credential lookup. Underlying runtime/network implementation is outside this package audit.

**Conclusion on the empty context:** it closes the default auth resolver's environment and file-existence probes. It does not close direct `PI_OAUTH_CALLBACK_HOST`, Bun proxy environment lookup on the WebSocket path, caller-provided auth overrides, the injected credential store, or the separate CLI's `auth.json`. For the broker's registered OAuth-only Codex provider, there is no `OPENAI_API_KEY` path (`broker/exo-model.mjs:102-107`; `broker/node_modules/@earendil-works/pi-ai/dist/providers/openai-codex.js:6-20`).

## Error material and logging

The inspected Codex package paths do not themselves call `console` or write logs during `Models` auth resolution, OAuth, or streaming. They **can throw or emit errors containing raw response data**: OAuth non-2xx token exchange/refresh embeds `response.text()`, and malformed successful token JSON is stringified (possibly including one token when another field is missing) (`broker/node_modules/@earendil-works/pi-ai/dist/auth/oauth/openai-codex.js:96-105,112-144`). Device start and poll errors embed raw response text or malformed JSON, including the success poll body when required fields are missing (`broker/node_modules/@earendil-works/pi-ai/dist/auth/oauth/openai-codex.js:153-169,191-225`; `broker/node_modules/@earendil-works/pi-ai/dist/auth/oauth/device-code.js:42-48`). A refresh failure's error message is carried into `ModelsError` via the cause formatter (`broker/node_modules/@earendil-works/pi-ai/dist/auth/resolve.js:77-97,1-18`; `broker/node_modules/@earendil-works/pi-ai/dist/utils/diagnostics.js:1-6`).

For streams, a non-2xx SSE response can become a thrown raw body or server `error.message`; failed SSE events can stringify the event; the final assistant error carries the formatted message (`broker/node_modules/@earendil-works/pi-ai/dist/api/openai-codex-responses.js:283-302,340-349,526-542,1224-1245`). WebSocket fallback diagnostics can also retain an error message and stack in an assistant message, though the broker forces SSE (`broker/node_modules/@earendil-works/pi-ai/dist/api/openai-codex-responses.js:228-245`; `broker/node_modules/@earendil-works/pi-ai/dist/utils/diagnostics.js:8-24`). The separate pi-ai CLI prints an uncaught login error's message to stderr, which could log that raw material if that CLI is used (`broker/node_modules/@earendil-works/pi-ai/dist/cli.js:109-112`). These are **possible content exposures if a server returns sensitive material**, not proof that OpenAI ordinarily does so. The package does not redact such text.

## Broker comparison and concrete gaps

- **Good isolation in current path:** broker registers only the OAuth-only Codex provider, supplies an empty auth context, stores credentials at `$EXO_MODEL_HOME/secrets/openai-codex.json`, requires OAuth before streaming, and passes the derived access token into direct Codex SSE (`broker/exo-model.mjs:15-20,53,102-107,147-160`; `broker/lib/store.mjs:55-64`). This does not consult `OPENAI_API_KEY` or pi-ai CLI `auth.json` in the ordinary broker path.
- **SSE identity is overridden:** `honestFetch()` replaces `originator` and `User-Agent` after pi-ai creates the headers, and `transport: 'sse'` ensures it is used (`broker/exo-model.mjs:95-99,157-160`; `broker/node_modules/@earendil-works/pi-ai/dist/api/openai-codex-responses.js:267-272,1275-1279`). This does not alter OAuth identity.
- **Browser identity gap:** browser login still prints pi-ai's `originator=pi` authorize URL because broker forwards `event.url` unchanged (`broker/exo-model.mjs:283-297`; `broker/node_modules/@earendil-works/pi-ai/dist/auth/oauth/openai-codex.js:229-243,354-368`). This conflicts with any claim that *all* OpenAI-bound originators are `exomachina`; it does not change the agreed SSE requirement in `INTERFACES.md:106`.
- **OAuth request identity gap:** refresh, device start/poll, and token exchange use the broker's patched global fetch, but that wrapper only restricts destinations and redirects; it does not set `originator` or broker `User-Agent`, and pi-ai supplies neither for these endpoints. The hard-coded pi-ai OAuth `client_id` remains (`broker/exo-model.mjs:89-99`; `broker/node_modules/@earendil-works/pi-ai/dist/auth/oauth/openai-codex.js:22,112-150,176-190`). There is no public pi-ai option for replacing this client ID.
- **Direct environment gap:** broker does not clear or reject `PI_OAUTH_CALLBACK_HOST`; browser login can use it despite the empty auth context (`broker/exo-model.mjs:102-107,283-297`; `broker/node_modules/@earendil-works/pi-ai/dist/auth/oauth/openai-codex.js:36-37,292-295`). The broker's `EXO_MODEL_HOME` and fixture `EXO_CODEX_BASE_URL` reads are intentional application config (`broker/exo-model.mjs:15-24,39-50`).
- **Filesystem boundary gap:** broker verifies canonical secret/credential paths only when `EXO_CODEX_BASE_URL` is set; without that override, `FileCredentialStore.read()` follows a symlink at the credential path, and `ownerOnlyDirectory()` follows a symlink for directories (`broker/exo-model.mjs:39-53`; `broker/lib/store.mjs:12-15,55-64`). A symlink or caller-supplied home can therefore make the injected store read a file outside its intended secret path, irrespective of `authContext`. This is a potential path-isolation failure; no such symlink was created or inspected in this audit.
- **Error boundary is currently generic:** broker classifies pi-ai errors but returns fixed public messages and logs only IDs/model/timing/kind, so the raw package errors above do not appear in the current socket error replies or event log (`broker/exo-model.mjs:109-124,141-145,163-179,250-251,349-352`). Its `redact()` is applied per socket line and replaces current full token strings and JWT-shaped strings, but is not a general sanitizer for arbitrary response-body fragments or a token split across multiple event frames (`broker/exo-model.mjs:70-82,167-173,233-235`). Avoid adding raw error logging without explicit redaction.

## Handoff

Only this file was added. Inspection was static: `sed`, `nl`, `rg`, `find`, `ls`, `stat`, `wc`, `cat`, and `git status` against the interface, installed package, and current broker. Reads passed. One ancillary `rg` returned exit 1 (no matches), and an initial broad `rg` included a nonexistent `dist/oauth` path before the actual `dist/auth/oauth` path was inspected; neither affected the findings. No test, login, credential-file read, network request, or mutation of product files was performed. The findings are limited to installed pi-ai 0.87.1 and the broker snapshot cited above; they do not assert live OpenAI acceptance of identity headers or URLs.
