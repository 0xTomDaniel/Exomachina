# Zigflow on Temporal, with managed worker rollout accepted

23 September 2026 · macOS arm64 · bounded local reassessment, **not production qualification**

## Decision

**Zigflow v0.15.2 re-enters the serious top-candidate comparison as a conditional Temporal authoring route.** A new definition requiring a Zigflow worker rollout is compatible with the clarified product contract: the bundled engine can start and manage its own workers automatically; active runs must stay on the exact published factory version; publication must never deploy or restart independent directory agents. Worker restart itself is no longer a negative finding. The prior no-refresh gate was a requirement mismatch, not an engine defect.

This trial established a workable local publication sequence with three graph revisions and separate worker versions. It also found a **real activation race**: an unguarded `set-current-version` success followed immediately by a new start once routed that run to the previous version. A publication controller must hold new starts until routing is observably on the intended build, or start each run with an explicit version override. This is manageable rollout work, not a reason by itself to discard Zigflow. The guarded trial used two harmless, signal-waiting canaries per version and then verified the actual new run's pin. That canary tactic is specific to this side-effect-free fixture; a product needs a safe release barrier and rollback policy.

Zigflow does not yet outrank the more complete Dagu/Effect product-shaped trials. Its full factory semantics, generic A2A recovery, secure packaging, and retained-version cost remain open. The existing product-owned Python interpreter remains a valid alternative, but it should now be compared on **total owned language/validator/rollout cost**, not on avoiding a restart.

## Observed local evidence

The single `python3 probe.py` invocation on a **prepared host** created a fresh PostgreSQL 16.15 cluster, started non-development Temporal Server v1.32.0, launched the independent Strands/A2A 0.3.0 capability fixture, and managed Zigflow v0.15.2 workers. It used the existing verified binaries and A2A virtual environment from the 22 September trials. This is one-command *trial startup*, not a clean-machine one-install product package. Loopback trust PostgreSQL and `--allow-no-auth` Temporal are trial-only settings. [Probe](probe.py), [definitions](definitions), [machine-readable result](observed.json), and [server template](server.template.yaml) are retained here; mutable databases and logs remain under the `state_dir` named in the result.

An earlier unguarded invocation is recorded in [activation-race.json](activation-race.json): after `set-current-version` succeeded for v3, `zig-reassess-v3` pinned to v2 and returned the v2 result. The retained server log later shows v3 becoming current. This specifically falsifies treating command success alone as a safe publication acknowledgement. The guarded final invocation passed; its two canaries and its real run all pinned correctly for each version. A single-host success does not prove routing behavior under concurrent publication, multiple Temporal frontend nodes, or a failing worker.

PostgreSQL had 49 processes in these samples; Temporal was one process; Zigflow added one process for each active retained version. The v3 deployment view reported v1 and v2 as `draining` while their waits remained open. Temporal's [Worker Versioning model](https://docs.temporal.io/worker-versioning) says pinned workflows stay on one deployment version and old versions can keep polling until their runs drain. This trial did **not** automate safe retirement after drainage, test thousands of retained versions, or measure a complete Strands/Director product bundle.

## Architecture and A2A cost

Zigflow supplies a real declarative DSL, structural validator, worker compilation, and durable Temporal execution. Its [run command](https://zigflow.dev/docs/cli/commands/zigflow_run/) loads definitions at worker startup and exposes versioning flags; `--watch` is labelled for development. A product publisher would still own the small external **publication Interface**: validate Exomachina policy and approved primitives, create an immutable content-addressed definition and dependency closure, launch the corresponding worker, verify route activation, expose the new version for run starts, retain/restart old workers while reachable, and retire them safely. The rollout controller is a real Module; treating `zigflow validate` as the whole publication gate would leave review, acceptance, capability binding, and dangerous `run.script`/`run.shell` permissions unchecked. Zigflow's [Run task documentation](https://zigflow.dev/docs/dsl/tasks/run/) and [dedicated-image warning](https://zigflow.dev/docs/deployment/dedicated-image/) make that primitive boundary explicit.

For a black-box remote A2A service, Zigflow's [HTTP Activity](https://zigflow.dev/docs/examples/http-call/) can send a protocol request, but a reusable A2A Adapter still has to identify the approved service and protocol revision, bind assignment/run/definition IDs to a remote Task ID, wait or poll, validate exact artifacts, handle cancellation, and reconcile a lost acknowledgement. The [A2A 0.3 specification](https://a2a-protocol.org/v0.3.0/specification/) provides `message/send`, `tasks/get`, and `tasks/cancel` by Task ID; it does not provide a universal lookup by caller action ID after a reply containing the Task ID is lost. Zigflow also [documents at-least-once HTTP effects](https://zigflow.dev/docs/dsl/tasks/intro/) and says the receiver must enforce any idempotency key. The existing [Temporal arbitration Adapter](../../2026-09-22/arbitration/temporal/adapter.py) and [A5 result](../../2026-09-22/arbitration/temporal/result.md) show the shared distinction: a participating receiver with action lookup can reconcile one effect, while an opaque receiver must remain unresolved rather than be blindly submitted again. This trial only proved the A2A service stayed independent and callable; it did not prove that Zigflow's HTTP task implements this complete Adapter. A separate gateway or custom Temporal Activity worker may be needed for a reusable, durable A2A lifecycle.

The alternative [stable Python interpreter trial](../../2026-09-22/round-two/temporal/result.md) published v2 without changing its worker PID and held old/new definitions in one worker. The later [arbitration implementation](../../2026-09-22/arbitration/temporal/result.md) counted about 337 maintained lines for its interpreter/worker and 304 for validator/catalog, plus shared A2A/Director and supervisor code. Line count is descriptive, not a quality or maintenance score. Zigflow can remove much of the generic graph interpreter Implementation, but it still needs Exomachina semantic checks, dependency binding, a publication catalog, worker-rollout machinery, A2A reconciliation, and safe interpreter-version upgrades. Python avoids one new worker process per published waiting version, while Exomachina owns the graph language and replay-compatible interpreter code. Neither route has passed full factory qualification.

## Limits and next decision gate

The three test graphs only wait for a signal and set data. They do not test nested factory selection, independent Quality acceptance, protected promotion, runtime-sized fan-out, full A2A Task recovery, concurrent publication, an uncooperative remote service, safe version retirement, or the E01–E10/M01–M08 product scenarios. A pinned Zigflow worker binds the tested definition to that run; it does not by itself freeze external capability code, Agent Cards, policy revisions, profiles, or artifact contracts. Exact **factory-version** binding needs that wider closure in the publisher.

The current official [Zigflow v0.15.2 release](https://github.com/zigflow/zigflow/releases/tag/v0.15.2) is marked Latest as checked on 23 September; its pinned source [license](https://github.com/zigflow/zigflow/blob/v0.15.2/LICENSE) is Apache 2.0. This checks the upstream source baseline, not the complete redistributable binary bundle, notices, PostgreSQL configuration, authentication, backups, or clean-machine one-install/start experience. Advancing it against Dagu, Effect, and the Python interpreter requires one matched product-shaped Strands/A2A factory run and serial whole-install resource comparison, including a publication and retention policy that proves the old version remains available until its last run drains.
