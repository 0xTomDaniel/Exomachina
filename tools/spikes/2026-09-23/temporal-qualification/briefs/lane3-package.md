# Lane 3 (`tw_package`): native one-command package, operations and resources

Owned directory: `tools/spikes/2026-09-23/temporal-package-ops/`. Ports 43000–43999. State `/tmp/exo-tq-package-*`. Follow [`../COORDINATION.md`](../COORDINATION.md), including the safety boundary. The data volume has about 20 GiB free: prefer existing pinned binaries; if you must fetch artifacts, keep them small, verify checksums, record sources, and delete them afterwards.

## Question

Can one native install/start command (no Docker) lay down and manage a self-contained Temporal Server + PostgreSQL + Python worker + Strands Director bundle on a clean macOS arm64 machine, with owned backup/restore, schema migration and endpoint protection, and what does the full bundle cost?

## Work

1. **Package feasibility.** Build a prototype `exo-factory` installer/launcher (script plus manifest) that installs into a fresh prefix under `/tmp/exo-tq-package-*`: Temporal server + sql-tool + schema, PostgreSQL binaries, a pinned Python runtime/venv with locked deps, the factory worker, Director and supervisor. Show it starts everything with **one** command and stops cleanly. Approximate a clean machine: run with `env -i` and a minimal `PATH`, no Homebrew paths, and audit every binary's dynamic dependencies (`otool -L`) and absolute path references for anything outside the prefix or macOS system libraries. Record what still depends on the host (e.g. Homebrew PostgreSQL dylibs, uv, Python) and the realistic remedy (relocatable PostgreSQL build, python-build-standalone, code signing/notarization). Record bundle size on disk.
2. **Backup/restore.** With a factory run ordinarily waiting at a Director decision: gracefully stop or use a consistent online backup (`pg_dump`/`pg_basebackup`), restore into a **fresh** prefix/cluster, start with the one command, confirm the same run is visible and can complete normally through the Director. Record RPO/RTO observations and what product state outside PostgreSQL (Director Task store, incident ledger, publication catalog, keys) must be in the same backup set.
3. **Migration.** Show the owned schema path: `temporal-sql-tool` setup/update-schema versioning on the bundled cluster, the installer's idempotent re-run, and a documented upgrade procedure (Temporal patch/minor schema update, PostgreSQL major upgrade via `pg_upgrade` or dump/restore). Run what is safe and ordinary; mark the rest as source inference.
4. **Endpoint protection.** Replace trial-only `trust`/`--allow-no-auth`: PostgreSQL with scram-sha-256 on loopback or a Unix socket in a 0700 directory; Temporal frontend bound to loopback with mTLS (self-signed per-instance CA generated by the installer) or at least a documented authorizer; Director A2A endpoint with a bearer token or mTLS; file permissions on secrets. Verify ordinarily that an unauthenticated client is refused and an authenticated one works. This is standard configuration verification on your own loopback services, not an attack.
5. **Resources.** Measure the complete bundle with the same macOS `footprint -f bytes --noCategories` selection used in `temporal-recovery-scale/held_assignment_probe.py`, at idle and with 0/2/10 ordinary waiting runs, plus PostgreSQL tuning variants (e.g. `shared_buffers`, `max_connections` lowered; Temporal persistence `maxConns` lowered) to show how much of the 761 MB / 50-PID baseline is configurable. Record disk usage growth.
6. **Memory ceiling.** The owner has **not set** a per-install memory ceiling. Do not invent one as a pass/fail threshold. Provide an explicit account: measured envelope, the tunable floor you observed, and what decision the owner must make (e.g. candidate ceilings with consequences). Mark it an open owner decision.

Do not kill processes or inject failures; use graceful stop/start and ordinary operations only.

## Output

`result.md`, `observed.json`, the installer prototype and scripts. Verdict per sub-gate (package, backup/restore, migration, endpoint protection, resources, memory ceiling), each observed / source inference / unproved.
