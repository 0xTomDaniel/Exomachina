# S0 countertrial — Kestra OSS v2.0.3 native standalone

**Result:** **Behavioral package gate passed; distribution/installer gate remains conditional.** The pinned GitHub OSS standalone artifact ran natively on macOS arm64 with Temurin JDK 25 and PostgreSQL 16.15. It published and completed a native `Log` workflow. A second workflow reached `PAUSED`; the launcher stopped both Kestra and PostgreSQL, restarted them with the same disk state, observed the same execution still `PAUSED`, resumed it through the v2 API, and observed the downstream task and whole execution `SUCCESS`. No Docker, vendor key or H2 mode was used. The product's one-install package is not finished: PostgreSQL was installed locally through Homebrew for this test rather than bundled with the harness.

## Reproduction and observed behavior

The test files and executable are in `/tmp/exomachina-spikes/s0/kestra`:

- `config.yml` configures `kestra.repository.type=postgres`, `kestra.queue.type=postgres`, JDBC URL `jdbc:postgresql://127.0.0.1:25432/kestra`, and persistent local storage under `data/storage`. It configures mandatory OSS Basic Auth with a random test credential. The credential is also in `api.netrc` (mode 0600); do not copy it into reports. `micronaut.server.host=127.0.0.1` binds the test API locally.
- `start-native.sh` is the bounded one-command test launcher. It initializes/starts the isolated PostgreSQL cluster and database as needed, launches `./jdk25/Contents/Home/bin/java -Xms256m -Xmx1g -jar kestra-2.0.3 server standalone -c config.yml --port=28080 --worker-thread=4 --no-tutorials`, and stops PostgreSQL on normal Kestra exit. The installed Homebrew PostgreSQL binary path is an external test prerequisite; a distributable bundled helper has not been made.
- `hello.yml` uses `io.kestra.plugin.core.log.Log`, included in the release JAR. `POST /api/v1/main/flows` returned HTTP 200, flow revision 1. `POST /api/v1/main/executions/exomachina.spike/hello` yielded execution `3Rv9vUVq8tnJKCWNE53Tyi`; `GET /api/v1/main/executions/{id}` reported `SUCCESS` and its Log task `SUCCESS`.
- `pause.yml` uses a Log, `io.kestra.plugin.core.flow.Pause`, and a downstream Log. Creating and starting it yielded execution `6GjJyyptNXTAtTRpQQ2Am4`; `GET` reported `PAUSED`, with the first task `SUCCESS` and Pause task `PAUSED`. After stopping and restarting **both** Kestra and PostgreSQL, `GET` still reported that exact execution and task state. The earlier completed execution still reported `SUCCESS`. The live v2 OpenAPI gives `POST /api/v1/{tenant}/executions/{executionId}/actions/resume`; it returned HTTP 200, and later `GET` reported the Pause, downstream Log and whole execution `SUCCESS`.
- `GET http://127.0.0.1:8081/health` returned HTTP 200 after startup. OSS API requests without Basic Auth returned HTTP 401. Official [Basic Auth troubleshooting](https://kestra.io/docs/administrator-guide/basic-auth-troubleshooting) says `enabled: false` is ignored; a credential is required. An earlier documented `/resume` route returned 404; the live 2.0.3 OpenAPI's `/actions/resume` route worked.

The [runtime and storage guide](https://kestra.io/docs/configuration/runtime-and-storage) identifies PostgreSQL as the normal production queue/repository path and H2 as local development. Local storage is appropriate for a standalone node with a persistent filesystem. This trial used PostgreSQL throughout; it makes no H2 production claim.

## Observed footprint and limits

- Published executable: **124.3 MiB** (`130,371,660` bytes); unpacked JDK 25: **294 MiB**; isolated PostgreSQL data after two small flows/restarts: **65 MiB**. These are local measurements, not installer totals.
- One warm idle Kestra process after the workflows: about **650 MiB RSS** with `-Xmx1g` and four worker threads. PostgreSQL's main process was about **23 MiB RSS** with multiple connection children; their RSS must not be summed naively because pages are shared. No sustained-load, CPU or peak-memory benchmark was run.
- In two restarts, the PostgreSQL log showed database-ready at `14:12:39.139` and Kestra-ready at `14:12:42.512`, then database-ready at `14:13:42.283` and Kestra-ready at `14:13:46.946`: roughly **3.4–4.7 seconds from database readiness** in this warm local test. It excludes cold artifact/JDK install and product launcher setup. The official [requirements page](https://kestra.io/docs/administrator-guide/requirements) recommends at least 4 GiB RAM and 2 vCPU for standalone; this tiny run does not revise that guidance.
- No vendor key was configured, but outbound network access was available during the run. Offline startup and full transitive license clearance are untested. The protected application API and the one-org-per-installation architecture still need their own Factory Module authorization tests.

## Follow-on dependency license audit — bounded closure of 97 missing declarations

The released JAR exposes 159 distinct Maven coordinates through `META-INF/maven/*/pom.properties`. The initial inspection found a declared license for 62 in embedded POMs and a metadata gap for 97. The follow-on script `audit_deps.py` fetched each of those 97 exact-version POMs from Maven Central and followed published parent POMs at most four levels; `pom-license-audit.csv` records every coordinate, POM chain, license text and retrieval status. **96 of the 97 gaps were missing *embedded* metadata only:** their license declarations were found in parent POMs. Typical examples are [Guava's parent](https://repo.maven.apache.org/maven2/com/google/guava/guava-parent/33.7.1-jre/guava-parent-33.7.1-jre.pom), [Netty's parent](https://repo.maven.apache.org/maven2/io/netty/netty-parent/4.2.18.Final/netty-parent-4.2.18.Final.pom), and [Docker Java's parent](https://repo.maven.apache.org/maven2/com/github/docker-java/docker-java-parent/3.7.1/docker-java-parent-3.7.1.pom). This establishes the published declarations for those exact components, not legal clearance of the final distribution.

The combined 159 POM declarations contain Apache, MIT, BSD, Eclipse Distribution License, EPL and some dual-license variants. Five Logback components declare EPL **or** LGPL alternatives in their [published parent POM](https://repo.maven.apache.org/maven2/ch/qos/logback/logback-parent/1.5.37/logback-parent-1.5.37.pom) and the older [Logback contrib parent](https://repo.maven.apache.org/maven2/ch/qos/logback/contrib/logback-contrib-parent/0.1.5/logback-contrib-parent-0.1.5.pom). The declared licenses do not show a use-case restriction like Orkes Article 3.3. Distribution notices, attribution and any copyleft option chosen still need assessment for the actual bundle; an EPL/LGPL name alone is not a commercial-use ban.

**One embedded component remains unresolved: `com.sun.xml.bind.jaxb:isorelax:20090621`.** Its [published POM](https://repo.maven.apache.org/maven2/com/sun/xml/bind/jaxb/isorelax/20090621/isorelax-20090621.pom) and inherited `jvnet-parent-3` POM lack a `<licenses>` declaration. The POM *file's own header* refers to GPLv2 or CDDL, but that does not establish one license for every bundled class. In the exact [published source JAR](https://repo.maven.apache.org/maven2/com/sun/xml/bind/jaxb/isorelax/20090621/isorelax-20090621-sources.jar), 9 of 42 Java files have an MIT-style permission grant and 33 have no license header. The release JAR contains 38 relocated `org_isorelax` class entries inside `com/ctc/wstx/shaded/msv/`, consistent with [Woodstox's explicit shading configuration](https://github.com/FasterXML/woodstox/blob/woodstox-core-7.2.0/pom.xml). Woodstox's open [license-notice issue](https://github.com/FasterXML/woodstox/issues/130) independently identifies uncertainty about shaded third-party notices. This is a **distribution-license and notice question to resolve before packaging Kestra** or a reason to evaluate a build without that optional XML-validation path; it is not evidence of a noncommercial or competitive-product prohibition.

The audit is bounded to components with Maven metadata inside this specific executable and their published POMs. It did not enumerate every class origin, verify the full license text/NOTICE assembly, inspect all optional Kestra plugins, or clear the Temurin and PostgreSQL bundle. No legal clearance is asserted. Product selection can use the proven runtime behavior while keeping package distribution conditional on closing the single unclear shaded component and the rest of the final-bundle review.

## S0 decision

Kestra OSS has a concrete native, Docker-free production-backend path and can be used for **bounded behavioral S1–S4 trials**. Final product selection remains conditional on a one-install package that bundles/manages its JDK and PostgreSQL helper, a complete dependency and redistribution review, and measured footprint against an agreed operating envelope. The test launcher proves lifecycle and durable state on this machine; it is not that final package.
