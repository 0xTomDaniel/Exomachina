# Independent decision-round judgment

22 September 2026. This is an independent, provisional product judgment from the three [candidate reports](.) and their executable probes, using the [common evaluation contract](common/EVALUATION.md). It is not a new engine test or a production qualification. The intended first product is a Strands Director/factory harness with separately identified capability and Quality instances, one-command launch with bundled local helpers allowed, one organization per deployment, agent-authored versioned factories, no required Docker or separately managed service, and an eventual path to multiple customers.

## Provisional preference

1. **Dagu, narrowly.** Its native, inspectable YAML DAGs and named child DAGs are the closest existing authoring surface to a catalog of agent-authored factories. The [trial](dagu/result.md) published a structurally different v2 while v1 waited, retained each named child closure across a Dagu restart, executed actual Strands/A2A assignments and independent Quality, and resumed after a receiver committed work but dropped its acknowledgment. A later bounded [Director bridge](dagu/director_trial.py) also used the Strands harness/A2A shell, recovered original Task IDs and exact accepted artifacts after Director SIGKILL, and rejected a stale Director incarnation. A further acceptance-gap trial committed exact acceptance, forced the review command to exit before Dagu marked the step complete, then recovered through explicit `dagu retry --step review --downstream` after Dagu had failed the run. It preserved one accepted revision and one local release, but **did not auto-resume from an outbox**; Exomachina must detect, authorize and command that retry. These follow-on observations in `/tmp/exomachina-decision-dagu-director4/director-result.json` and `/tmp/exomachina-decision-dagu-gap-root-1/result.json` are separate from the passing core run. A two-home test found Dagu's host-global `/tmp` socket collides when both homes use the same DAG and run ID; different run IDs let both execute. Exomachina must allocate host-globally unique physical run IDs, bound to each durable harness identity, even when two installs use the same factory definition. Dagu remains the shortest credible route to factory publication without implementing a general graph interpreter. The publisher, capability binding, semantic policy, A2A reconciliation, exact acceptance, recovery policy and catalog transaction still belong to Exomachina. Dagu is GPL-3.0-or-later; commercial use and a separate bundled CLI/server remain eligible under the operator's GPL-compliant-distribution review posture. The current bundle includes Dagu's license text but **not its Corresponding Source or a verified source-delivery path**. [Independent GPL review](dagu/gpl-bundle-review.md) also leaves the final aggregate-versus-combined-work boundary and customer terms for actual-product review.
2. **Effect Workflow/Cluster, close second and the durability leader in this round.** The [trial](effect/result.md) used one unchanged SQLite-backed helper for two pinned factory versions, actual Strands/A2A workers, a durable Director wait, helper hard crashes during uncertain remote work and at both sides of the acceptance-to-workflow signal, stable outbox replay, and a local two-helper same-run contention test. The Strands Director/A2A follow-on recovered the original Task after its process restarted. A [copied-bundle trial](effect/packaging-result.md) added in-bundle Node and Python runtimes, one-command supervision, two Directors sharing one helper, separate Director/helper crash recovery, and hard-kill/relaunch of the outer supervisor on persisted ports; both original Tasks completed. The direct pinned Effect packages had no encountered commercial gate and the tested stack avoided Java and Docker. The central cost is structural: the current 292-line helper recognizes only **two fixed linear definition shapes**. Branches, parallel joins, nested factory closures, bounded repair loops, safe publication, validation feedback, and maintenance/autoresearch are not provided by that document language. A production DSL/interpreter and policy would be a core Exomachina Module, not a small A2A adapter. The copied bundle is not a clean-machine, portable or redistribution-qualified installer; production supervisor policy and a safe shared-helper boundary remain product work.
3. **Strands Graph.** Its [trial](strands_graph/result.md) gives the cleanest same-language Director/harness integration: the follow-on factory endpoint reused the Strands tool loop and A2A task path, and Graph sessions resumed after a Director process crash. Strands Graph itself supplied graph progression and session restore. Exomachina supplied publication/validation, A2A calls, local claims, remote reconciliation, acceptance, outbox and delivery fencing. A general agent-authored, managed factory catalog would require a definition interpreter and durable external scheduling/ownership/recovery around Graph. That risks building much of the workflow engine in product code. The trial's two parallel capability calls were execution-shape evidence: Quality reviewed only one branch, so it did not prove a meaningful joined research factory. The A2A call sat in a spike-only model `stream` adapter, not the intended production worker Interface.

This ordering weights the *whole product* and the requirement that an agent can publish a new factory composition without a code rollout. If the requirement shifted toward a few developer-coded workflows with more stringent local crash recovery, Effect would move first. Dagu's lead is conditional on implementing bounded, authorized recovery after the demonstrated acceptance/engine fault and clearing its distribution questions; it is not a declaration that YAML is inherently safer or that its core run has stronger durability than Effect's.

All three used the same deterministic A2A 0.3.0 capability and Quality fixture. Its stable action-key receipt, immediate durable lookup and duplicate suppression are **not** supplied by any candidate engine or by generic A2A peers. Thus `accepted_count=1` does not mean an engine guarantees exactly-once remote effects. None tested A2A 1.x, opaque peers, asynchronous A2A task lifecycles, real model judgment, production credential boundaries, cross-host failover, or external publication exactly-once. The Effect and Graph Director follow-ons prove a bounded A2A integration; their test fixtures do not prove independent Quality authorization. In particular, Effect's Director currently sends a reviewer identity string from the helper ledger to acceptance rather than a credential or verified Quality result with authority.

The process measurements are **launcher observations, not a controlled benchmark**. Dagu's original waiting parent was about 106 MiB RSS plus roughly 117 MiB for each Strands endpoint, excluding short-lived Dagu children. The latest **shared-Dagu** copied bundle with two Directors and its own managed CPython runtime and Dagu license files had about 314 MiB of disk use. Its subsequent long-running [supervisor](dagu/supervisor.py) trial in `/tmp/exomachina-decision-dagu-supervised3/state/bundle-result.json` restarted killed children and hard-killed/relaunched the outer supervisor on persisted ports; B finished while A was down, and both original A2A Tasks survived Dagu and supervisor restarts. Seven sampled process-tree PIDs summed to **692,048 KiB (675.8 MiB)** warm RSS. Effect's [copied bundle](effect/packaging-result.md) used about 393 MiB disk, with in-bundle Node/Python; its own outer-supervisor kill/relaunch also recovered both original Tasks, and six warm processes with two waiting runs summed to **690,160 KiB (674.0 MiB)** RSS. These are close broad shared-helper topologies, so neither has a demonstrated warm-memory advantage. Both supervisors are product-owned and only tested settled waits, not every child-spawn/registry crash gap. Neither shared-helper launch proves two independent harness installations can run together. A separate Dagu namespace probe in `/tmp/exomachina-decision-dagu-namespace2/namespace-result.json` found that two Dagu homes with the same DAG name and run ID collide at a host-global `/tmp/@dagu_…sock`; per-instance `TMPDIR` did not fix it, whereas distinct run IDs let both root and child DAGs succeed. Graph's three-process Director topology sampled about 124 MiB Director and 119 MiB for each endpoint; its graph sent two capability assignments versus one in the other trials. None has a clean-machine, portable, redistribution-qualified installer, full transitive license inventory, or comparable peak-physical-memory measurement. Dagu's GPL obligations are material but not a demonstrated prohibition; Effect and Strands metadata are friendlier, yet their full redistribution packages are also unreviewed.

## Engineering and optional autoresearch

The accepted [factory-maintenance architecture](../../../../docs/factory-maintenance.md) requires incident deduplication and fenced recovery, bounded retry/breakers, an independent watcher for engine failure, preserved artifacts, independently evaluated process improvements, immutable active-run bindings, controlled promotion/rollback, and protected production capacity. Optional autoresearch adds bounded isolated experiments, immutable evaluators, held-out comparisons, and stop conditions. Its **M01–M08 and R01–R05 scenarios are all unrun**; no candidate earns a support mark from these trials.

Each engine has a plausible extension path, with different product cost. Dagu's native versioned YAML and child compositions are a natural output for Engineering proposals, but Exomachina must make publication atomic, validate safety beyond syntax, preserve closure, and coordinate promotion with current-admission compare-and-swap. Effect's durable Activities/waits and outbox are useful for recovery and evaluation runs; proposals still need a far broader controlled DSL and interpreter. Graph can reuse the Strands harness and Graph construction, but its maintenance observer, leases, scheduler, publication catalog and replay boundaries would be substantially product-owned. All three need the independent watcher *outside* their execution loop, Quality authority, evaluator isolation, budgets, incident ledger, and a rule that improvements create new versions for future admissions rather than rewrite active runs. None supports self-healing or autoresearch merely because it can execute a retry or a graph.

## Most decision-changing next test

Give an authoring agent the same concrete **v3 factory request** on Dagu and Effect: two useful parallel capability results must join into one artifact; independent Quality may request a bounded repair; a nested verified subfactory is pinned transitively; a v2 run remains waiting while v3 is published and started. Feed each author the native or product document schema and actionable validator errors. Reject a review bypass, unbounded repair, wrong capability contract and mutation of an active closure. Require exact accepted output, a reproducible cold restart, and no *per-definition* worker or engine rollout once the approved vocabulary exists. Measure the product-owned interpreter, semantic validator, publication/reconciliation code and author correction loop—not only definition length or token count. If Effect supports this representative graph with a compact safe declarative layer, its stronger observed recovery and simpler direct source-license posture may make it first. If that requires building a second general scheduler/interpreter while Dagu composes it in native YAML plus bounded policy, Dagu's authoring advantage is decisive. This is a useful first development discriminator after a provisional selection, **not a newly mandatory pre-choice spike**. It does not replace the clean-install/license review or the still-unrun maintenance/autoresearch scenarios.
