# Effect product-shaped decision trial

22 September 2026. **Observed pass for these bounded runs.** One unchanged Effect Workflow/Cluster helper executed pinned v1 and v2 factory documents, called two separate Strands/A2A harness processes, survived an unresolved remote assignment and several helper crashes, and completed exact-revision acceptance through a product-owned outbox. A separate follow-on put the Director behind a real Strands/A2A endpoint backed by that helper. This is stronger than the earlier synthetic Effect trial. It is **not** a production qualification or evidence of exactly-once arbitrary remote effects. The deterministic Quality fixture decides acceptance; no live model evaluates quality.

## Reproduce and exact topology

From this directory on the tested macOS arm64 host, with Node.js 26.0.0, Python 3.14.3, and the pinned S2 virtual environment already installed:

```sh
npm ci --omit=dev
python3 probe.py /tmp/exomachina-effect-decision-repro
```

The [driver](probe.py) starts three local processes and owns their shutdown: one [Effect helper](helper.mjs) with its own HTTP endpoint; and two instances of the common [Strands/A2A harness](../common/harness_server.py), configured as capability and Quality, each with a separate endpoint, state directory, persistent identity and SQLite database. All three are launched by one *test* command; this is not a packaged one-install product. The helper uses two local SQLite databases: Effect SQL state and an Exomachina-owned product ledger. No Docker, Java, managed service, model provider, or remote infrastructure was used. A fourth Effect helper was launched only for the same-run contention trial. **The core trial had no Strands Director; the follow-on below adds one.**

The [observed JSON](observed.json) is from `python3 probe.py /tmp/exomachina-effect-decision-7`, a fresh directory. The pinned `package-lock.json` SHA-256 is `0249a14623d1248f7bc3368c9486205b86d984aa4b9adbeb052cd949eed31626`. Direct installed versions were `effect` 3.22.2, `@effect/cluster` 0.60.2, `@effect/workflow` 0.19.1, `@effect/sql` 0.52.1, `@effect/sql-sqlite-node` 0.53.0, and `better-sqlite3` 12.11.1. The remote Python dependency graph is the pinned [S2 uv lock](../../s2/uv.lock): Strands 1.57.0 and A2A SDK 0.3.26, advertising wire protocol 0.3.0. This does not establish A2A 1.x compatibility.

## Engine credit versus product code

Effect supplied the SQL-backed workflow execution ID, durable Activity replay, deferred Director wait and repeated signal behavior observed here. The fixed workflow interpreter was **our code**. The 292-line helper also implements the publisher/validator and run binding, A2A submit/status Adapter, artifact and Quality checks, acceptance ledger, outbox, local HTTP API, and delivery marker. The 321-line Python driver orchestrates faults and measurements; it is trial code, not runtime code. The common Strands/A2A receiver supplies stable action-key deduplication and lookup. The second remote submission after v1's crash was safe *because that receiver accepted the same key once*. We should not transfer that property to arbitrary A2A peers or to Effect.

The current language supports only two approved linear shapes; it does not establish arbitrary graph authoring, branches, parallel work, nested factories, repair loops, maintenance/autoresearch, or complete transitive capability pinning. Product catalog and workflow-start writes are in separate SQLite databases without a shared transaction; the trial exercised several recovery seams but not every crash point or durable startup reconciliation. The A2A Adapter polls a fixture-specific action lookup after an ambiguous send, and an unresolved action currently makes the workflow fail after a bounded wait rather than exposing a durable `unknown` state. Host-loss recovery, production authorization/TLS, cancellation, asynchronous A2A tasks, protocol 1.x, unified harness packaging, and a distributable one-install product remain open.

## Strands Director follow-on

The [Director adapter](director_server.py) reuses the S2 Strands model/tool loop, A2A executor and task-store path. It persists a distinct Director identity, incarnation, run binding and A2A task aliases in its own SQLite file. `start` forwards one pinned run to the Effect helper; `tasks/get` projects Effect state; `decide` requires the helper's independent Quality verdict, then forwards exact-revision acceptance and a stable outbox continuation. The Adapter does **not** choose or dispatch graph nodes. Its reasoning is still the deterministic model fixture. The capability and Quality endpoints come from the shared decision-round harness module, so this demonstrates a common Strands-based harness pattern rather than one finished shipping package for every role. **Authority is trial-only:** the Director passes the Quality identity string from the helper ledger into `/accept`; no credential proves that Quality itself authorized that acceptance. A product must derive acceptance from a verified Quality result or credential, not caller-supplied reviewer text.

Reproduce with the pinned S2 environment:

```sh
../../s2/.venv/bin/python director_probe.py /tmp/exomachina-effect-director-repro
```

The fresh [Director observation](director-observed.json) from `/tmp/exomachina-effect-director-1` passed. An A2A `message/send` to the Director started `director-run` and returned a task initially `working`. Its original task reached `input-required` without an accepted artifact. The Director process was killed and restarted against the same state: its identity remained unchanged, incarnation moved from 1 to 2, and A2A `tasks/get` recovered the original task at `input-required`. A repeated `start` received a new protocol task alias for the same logical run. A Director `decide` on the original task used the separate Quality verdict and completed it with the exact accepted artifact. The worker and Quality each recorded one accepted action, and the Effect product ledger recorded one delivery. The helper remained alive during the Director restart; the core trial above covers helper restart independently, not simultaneous failure of both processes.

At the Director wait the four process RSS samples were: Director **119,360 KiB**, Effect helper **210,416 KiB**, worker **117,744 KiB**, Quality **117,632 KiB**. These sum to about 552 MiB of per-process RSS, with shared-page double counting possible. This was on the same Mac but a separate run, so it is a topology cost indication, not a controlled benchmark or full packaged footprint. The Director Adapter is **229 lines** of product-owned Python; its **182-line** driver is trial code. The Director adds a fourth local HTTP port and fifth SQLite database. The subsequent [copied-bundle trial](packaging-result.md) adds a trial supervisor and exercises two Directors sharing the helper; production lifecycle policy and installer remain unbuilt.
