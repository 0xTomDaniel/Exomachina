Date: 22 September 2026. Final run: `python3 spike.py test /tmp/exomachina-spikes/s4/run2` (macOS arm64, Python 3 stdlib). Evidence: `run2/result.json` and three SQLite databases in `run2/`.

The custom HTTP receiver accepted `co-op-1`, then the caller process exited before recording its task ID. A new client process discovered the same task. A separate duplicate submission with the same action ID returned the original task ID; the receiver recorded one effect. A second receiver intentionally lacked discovery and duplicate handling. After the same lost reply, recovery recorded `unknown` and did not resubmit. One opaque effect remained.

The fixture rejected an approval for stale artifact revision `r1`, an author's attempt to approve `r2`, and a duplicate approval. Independent reviewer `quality-1` accepted `r2`, creating one durable outbox command. The product process then exited before calling the engine endpoint. A new process posted the command; it exited after the fake engine committed and before recording the acknowledgement. A final replay completed the outbox with one engine continuation.

**Observed:** four client process exits/restarts, one cooperative remote effect, one opaque remote effect, one accepted `r2`, one fake engine continuation, no unsafe resubmission of the unknown action. The server uses separate SQLite files to force the product/receiver/engine transaction gaps.

**Limit:** This is a deterministic product integration fixture. Its transport is custom HTTP, not A2A, and its engine endpoint is a stub, not Conductor, Kestra or another candidate. It proves a small intent/outbox/reconciliation shape can survive selected gaps; it does not show that an actual engine preserves graph ownership or that a real A2A peer can discover outcomes. Keep S4 open for one candidate-backed run after S0 identifies a permitted runtime. Do not credit the fixture's idempotency to the workflow engine.

The product-owned records in this slice are `assignments` (durable intent and observed remote task), `artifacts` (current and accepted revision/reviewer), and `outbox` (one cross-system completion command). The engine stub owns only received continuation IDs. Candidate integration must check that Exomachina does not grow code that chooses or dispatches the next graph node.

## Combined gated A2A → acceptance → delivery slice

`python3 gated.py test /tmp/exomachina-spikes/s4/gated-run1` published `a2a-gated.yaml` and started Kestra execution `113JtSAiptto3UKConxLKh`. Kestra's native HTTP task called the live Strands A2A 0.3.0 capability. The flow then reached `PAUSED` before delivery. The product process exited before reading the persisted task output; a new process recovered the A2A `completed` task and structured artifact from Kestra's task-output API. It rejected a stale revision and author self-approval, then recorded independent `quality-1` acceptance of the exact artifact digest and one durable resume command. A second forced exit occurred after product acceptance but before Kestra continuation; a third occurred after Kestra accepted resume but before the product recorded its acknowledgement. Replay observed Kestra's progressed state and closed the outbox. Final Kestra state was `SUCCESS`, with one task run each for assignment, quality wait and delivery. Evidence is `gated-run1/result.json`, `observed-a2a.json`, product SQLite and Kestra's retained execution.

**Bounded S4 finding:** the engine can own graph dispatch/wait/continuation while a small product ledger owns assignment correlation, exact-revision acceptance and cross-system command recovery. The separate custom receiver fixture proved a lost remote acknowledgement is recoverable with service-side discovery/deduplication, or remains explicitly unknown without it. The combined flow did **not** inject a lost response between the A2A service and Kestra's HTTP task; it recovered a lost product observation after Kestra had stored the response. It also used an immediately completed A2A task and deterministic Quality fixture. Asynchronous `input-required`/`auth-required`, long remote waits, cancellation and full A2A protocol coverage remain unproved. A production Adapter must use the same gate and cannot rely on HTTP 200 as semantic acceptance.
