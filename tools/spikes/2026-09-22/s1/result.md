# S1 — Kestra contested-state litmus

Date: 22 September 2026. Candidate: Kestra OSS 2.0.3, with the pinned artifact and JDK 25 from S0. This S1 instance has its own PostgreSQL 16.15 data at `data/postgres`, HTTP 28081, management 28082, worker controller gRPC 50052, and local storage. Its `start-native.sh` launches PostgreSQL and Kestra together. Credentials are isolated in mode-0600 local files and are not part of the result.

**Result: passed the narrow restart and contention cases tested; broader S1 remains unqualified.** Reproduce the workflow with `sh start-native.sh` in this directory, then `python3 probe.py create --url http://127.0.0.1:28081`; stop the launcher with SIGINT, start it again, then run `python3 probe.py check --url http://127.0.0.1:28081`. `python3 race.py` runs five more independent resume/kill races. The retained `pause.yaml`, `probe.py`, `result.json`, `race.py`, `race-results.json`, PostgreSQL data and Kestra log record the fixture and observations.

The reference execution `4pnlDPiv4tkAyDsNbsiJkb` reached `PAUSED`; both Kestra and PostgreSQL stopped; it returned as `PAUSED` after restart. Eight simultaneous resume requests produced one HTTP 200 and seven HTTP 409 responses. The execution reached `SUCCESS` and its downstream `after` task had one successful task run. The first local attempt used the obsolete resume path/JSON content type and received HTTP 415; the recorded passing attempt uses Kestra 2.0's `/api/v1/main/executions/{id}/actions/resume` with multipart form data. The first isolated server startup also exposed extra default ports (management 8081, gRPC 50051); assigning 28082/50052 resolved collisions with S0. These are packaging/configuration findings, not engine race failures.

Five paired resume/kill requests produced one terminal `SUCCESS` and four terminal `KILLED` executions. Every run remained in the same terminal state after observation; each had at most one downstream task run. The `SUCCESS` run's downstream task succeeded once; killed runs had none. Both control requests returned HTTP 200 in some races, so callers must inspect final execution state instead of treating a control response as the final outcome. This fixture has no external side effects.

The fixture used only a native `Log → Pause → Log` flow. It does not prove leased lock correctness, long outage handling, external effect idempotency, storage failure recovery, throughput, or behavior under multiple Kestra servers sharing one database. It qualifies this **single managed local server topology** only. A real service-side effect still needs its own idempotency/reconciliation contract.

Primary API references: [Kestra OpenAPI](https://kestra.io/kestra.yml), [Pause task](https://kestra.io/docs/workflow-components/tasks/flowable-tasks), [PostgreSQL runtime configuration](https://kestra.io/docs/configuration/runtime-and-storage).
